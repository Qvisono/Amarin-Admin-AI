# Аудит кандидатов для Rust: Amarin Admin AI

Дата: 7 ноября 2026 года. Проверена рабочая копия 1.38.0-beta.1.
Исходники приложения не изменялись. Анализ включает чтение кода и существующие бенчмарки Core. Приложение с реальным профилем, платные API и оконные бенчмарки не запускались.

## Вывод

Не найден класс, перенос которого на Rust уже доказанно даст кратный прирост всего приложения или запуска.
Есть измеренная медленная операция поиска, большой объём временных выделений при SSE и несколько вычислительных модулей, пригодных для эксперимента с Rust.
Основные конкретные находки связаны с повторной обработкой данных и работой до первого кадра. Сохранение этих алгоритмов при смене языка сохраняет причины затрат.

## Что измерено

Существующий Amarin.AdminAI.Benchmarks, Release, .NET SDK 10.0.401 / runtime 10.0.12, Windows 11 x64.
BenchmarkDotNet 0.15.8, InProcessEmitToolchain, 8 прогревочных и 12 измерительных итераций, целевая длительность итерации 250 мс.
Некоторые выбросы BDN исключил автоматически. Это локальный базовый замер C#, сравнения с Rust нет.
Обычный профиль не читался: данные созданы Fixtures во временной папке аудита, шифрование отключено, HTTP подставной.
Кэш файловой системы и прогретый JIT означают, что эти числа не описывают холодный старт EXE.

Выделенная память не означает постоянный размер RAM или утечку.
SaveOnUiThread периодически вызывает Flush в самом бенчмарке, поэтому это не строго изолированная синхронная часть.
Имя SearchRareWord историческое: KB5000039 повторяется в синтетических чатах; это измерение конкретного запроса, а не доказательство максимальной задержки отсутствующего запроса.
SaveDeferred измеряет подготовку/планирование, а не завершение записи на диск.

Первый прогон остановлен: атомарная перезапись файлов в системной временной папке песочницы запрещалась, включались повторы AppDataFile.
Второй прогон выполнен с TEMP/TMP внутри папки аудита и завершил все 12 сценариев за 97,63 с.
SaveTextIndex во втором прогоне всё ещё зарегистрировал исключения и большой разброс; его время исключено из выводов о производительности. Причина этих исключений отдельно не диагностировалась.
Невалидный первый прогон сохранён отдельно в benchmarks; использовать результаты benchmarks-workspace-temp.

## Кандидаты

### 1. ChatTextIndex: лучший измеренный кандидат для отдельного поискового модуля

Amarin.Core/ChatList/ChatTextIndex.cs:178-210.
Search сортирует записи по UpdatedAt, затем ищет подстроку в сообщениях через CurrentCultureIgnoreCase.
Редкий/отсутствующий запрос может проходить большую часть корпуса; ранний выход только после 200 находок.
Построение индекса уже выполняется фоном (UI/MainWindow.TextSearch.cs:17), поиск тоже идёт через Task.Run (:90-100).

Разумный Rust-эксперимент: постоянный индекс в Rust, инкрементальное обновление, возврат только найденных id/фрагментов.
Неразумно передавать весь корпус из C# в Rust на каждое нажатие.
Ускорение от структуры индекса нужно сравнивать и с аналогичной оптимизацией на C#.
Нельзя молча заменить культурозависимый Unicode-поиск ASCII lowercase или простым UTF-8 memmem: изменятся результаты и индексы выделения.
Первый кадр напрямую не ускоряется; фоновая сборка может конкурировать за CPU/диск.

### 2. ChatStreamAccumulator + VeniceClient: большой объём повторного копирования

Amarin.Core/Providers/ChatStreamAccumulator.cs:56-68.
Amarin.Core/Providers/VeniceClient.cs:641-644.
На каждый текстовый чанк вызывается onText со всем накопленным ответом.
Кэш Parsed убирает повторные чтения одного состояния, однако после следующего чанка _text.ToString снова копирует весь префикс.
При фиксированном размере чанков суммарный объём копирования растёт квадратично.
Рост 600 -> 4000 чанков дал примерно 33-кратный рост выделений памяти при 6,67-кратном числе чанков.

Первый эксперимент: уведомления дельтами и ограничение частоты формирования полного текста; сохранить корректную обработку reasoning и отмены.
Перенос парсера на Rust при прежнем callback полного C# string может сохранить квадратичное копирование.
18 мс здесь не означают секунды задержки реального ответа; UI и сеть не измеряются.
На запуск не влияет.

### 3. CodeHighlighter: удобная независимая граница

UI/CodeHighlighter.cs:54,190-281.
ColorCode формирует токены, SpanFormatter создаёт массив класса каждого символа, подстроки и склеивает соседние участки.
Класс не зависит от WPF; возможен Rust API с текстом на входе и интервалами токенов на выходе.
Нужно учесть кодировки и перевод UTF-8 offsets в UTF-16 позиции WPF.
Доля подсветки в стоимости UI не измерена; коэффициент ускорения не установлен.
На обычный первый кадр пустого чата не влияет.

### 4. AppearanceImageCache: подходящий вычислительный модуль для Rust/SIMD

UI/AppearanceImageCache.cs:422-549.
Saturate делает проход по пикселям с double; BoxBlur выделяет scratch; выполняются три размытия по двум осям.
Можно вынести обработку одного буфера BGRA в Rust и сравнить с C# SIMD/переиспользованием scratch.
Картинки уже уменьшаются, результаты кэшируются в RAM/PNG, Prewarm выполняет Task.Run.
На попадании в кэш фильтр не исполняется. Ускорение относится прежде всего к новым обоям/параметрам, а не всему запуску.
Время фильтра в этом аудите не измерено.

### 5. ChatStore + ChatAttachmentFiles: повторная обработка неизменных вложений

Amarin.Core/Storage/ChatStore.cs:623-682.
Amarin.Core/Storage/ChatAttachmentFiles.cs:57-77,138-188,228-250.
При новом тексте сериализуется весь чат с base64, считается отпечаток всего JSON.
Externalize снова проходит JSON, декодирует вложения и считает их SHA256; Decode также проверяет base64 обратным преобразованием.
Файл уже существующего blob не переписывается, но часть CPU-обработки повторяется.

Сначала отделить неизменные вложения от снимка переписки и кэшировать проверенные преобразования.
Rust уместен для цельного байтового конвейера хранения, если измерения больших вложений покажут необходимость.
Перенос только SHA256/base64 малообоснован: это уже библиотечные операции.
Запись фоновая; может влиять на общую нагрузку и открытие больших чатов.

### 6. ContextHygiene: потенциальная квадратичная работа на длинных историях

Amarin.Core/Chat/ContextHygiene.cs:132-182,362-434.
Для старых чтений файлов просматриваются другие вызовы с повторной нормализацией путей.
Версии блоков кода попарно сравниваются по наборам строк.
Сначала предвычислить пути/window, индексировать изменения и рассмотреть кэш неизменного обработанного head, сохраняя границы HygieneUpTo/кэша провайдера.
Потенциально большой локальный выигрыш на длинных агентских историях. Замеров нет. На первый кадр не влияет.

### 7. TableQuery / ExcelFormulas / DocumentConvert

Amarin.Core/Documents/TableQuery.cs:109,222,390; ExcelFormulas.cs:334; DocumentConvert.cs:73.
Материализация строк, повторные преобразования чисел в сортировке и промежуточные списки агрегатов.
На больших таблицах полезны типизация столбцов и агрегирование за один проход, независимо от языка.
Rust/columnar backend возможен, но численный выигрыш не измерен. К обычному запуску отношения нет.

## Более важная цель для плавности UI

AssistantMessageView.SetBody (UI/ChatMessageViews.cs:237) заново передаёт весь ответ в ChatMarkdown.Write.
UI/ChatMarkdown.cs:176 разбирает полный текст, :191 создаёт новый FlowDocument.
При streaming BuildCode (:496) отключает кэши и у завершённых неизменных code-блоков.
CodeBlockView.MeasureWidest (:318) снова создаёт FormattedText для строк.
Окно уже ограничивает частоту адаптивным таймером 80-500 мс (MainWindow.xaml.cs:30,3635), но объём повторной работы остаётся.

Первоочередная цель: переиспользование завершённых блоков, кэш подсветки/ширины неизменного кода и обновление хвоста.
Rust способен ускорить парсинг/подсветку, но создание, измерение и раскладка WPF останутся.
Стоимость этой цепочки в данном аудите не измерялась.

## Что конкретно проверить для ускорения запуска

1. ChatListLayout.Build в ChatOrganizer.cs:415-417 заново фильтрует loose для каждой папки. Можно сгруппировать один раз.
2. MainWindow.xaml.cs:3086 строит план всего списка, а :3095 только затем берёт первые строки для кадра. Ограниченный план первой порции уменьшит работу на больших профилях.
3. MainWindow.xaml.cs:3012 обновляет JumpList через Windows Shell до первого кадра. Проверить возможность отложить применение за кадр.
4. MainWindow.xaml.cs:341 вызывает CleanupLeftovers синхронно из Loaded. UpdateInstaller.cs:534-535 вызывает удаление каталогов; дисковую работу можно проверить на безопасное отложение.
5. AppSettingsStore.cs:54,135-136 и ProfileStore.cs:42,45,80-81 дважды десериализуют свежий JSON для проверки и чтения. Можно переиспользовать проверенный результат; большой эффект не установлен.
6. WPF InitializeComponent, загрузка ресурсов, первая раскладка остаются при гибриде C#/Rust.
7. В опубликованном EXE используется single-file compression; её влияние нужно отдельно измерять на идентичных вариантах упаковки. Флаги публикации не менялись.

ReadyToRun и multicore JIT уже предусмотрены; настройки, Роза и часть фоновых служб уже отложены.
Перенос отложенного класса сам по себе не сокращает путь первого кадра.

## Ограничения измерения запуска

Program.cs:252 останавливает PerfLog app_start перед app.Run(window), поэтому эта метка не включает Loaded, раскладку и первый кадр.
main_window_ctor охватывает InitializeComponent, не весь жизненный цикл запуска.
StartupBenchTests измеряет кадр тестового окна, но использует UiServices вместо полного AppComposition и показывает окно на экране. Его в этом аудите не запускали.
Холодный старт опубликованного EXE, загрузка CLR, single-file decompression и фактический первый кадр не измерялись.
Исторические цифры из CLAUDE.md не выдаются за текущие замеры.
Без этих измерений нельзя установить долю запуска, которую вообще мог бы сократить Rust.

## Приоритет действий

1. Для измеренной задержки поиска: отдельный индекс, затем сравнительный прототип C#/Rust с одинаковыми правилами поиска.
2. Для памяти потоков: delta/cadence API накопителя; для плавности отдельно инкрементальный рендер WPF.
3. Для запуска: точные метки ContentRendered и проверка ограниченного плана списка/отложенных Shell и disk операций.
4. Для небольшого Rust-прототипа: CodeHighlighter или пиксельный фильтр, но только с измерением и собственного времени, и полного пользовательского сценария.

Базовый замер доказывает стоимость существующего кода. Проценты и кратность выигрыша после изменений здесь не заявляются.
