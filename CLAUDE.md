# Amarin Admin AI — памятка для агента-кодера

WPF-приложение под Windows (.NET 10, `net10.0-windows`): чат с языковой моделью — Venice,
OpenRouter, напрямую у OpenAI, Anthropic и других провайдеров или через свой сервер человека, —
которая через локальные инструменты администрирует этот же компьютер.
Интерфейс и комментарии — по-русски, имена в коде — по-английски.

Ниже собрано то, на чём здесь легко ошибиться. Почти каждый пункт — уже случившаяся ошибка.

## Команды

```bash
# сборка
dotnet build "Amarin Admin AI/Amarin Admin AI.csproj"

# тесты — их 3500+; держите их зелёными
dotnet test Amarin.AdminAI.Tests/Amarin.AdminAI.Tests.csproj

# релизная сборка одним файлом (ровно эти флаги!)
dotnet publish "Amarin Admin AI/Amarin Admin AI.csproj" -c Release -r win-x64 \
  --self-contained true -p:PublishSingleFile=true \
  -p:IncludeNativeLibrariesForSelfExtract=true -p:EnableCompressionInSingleFile=true \
  -p:DebugType=none -o "release/publish-<версия>"
```

Про публикацию: без `IncludeNativeLibrariesForSelfExtract` рядом с exe остаются нативные
библиотеки, без `EnableCompressionInSingleFile` файл выходит 167 МБ вместо 78 МБ. Правильный
результат — один exe ~106 МБ плюс `appsettings.json` (1.32.0 был 94 МБ; с 1.28.0 в нём
разборщик PowerShell, `System.Management.Automation`, — около 10 МБ, с 1.33.0 — OpenXml и PdfPig
для документов, с 1.37.0 — обёртка и загрузчик WebView2 для браузера агента; документацию пакетов
рядом с exe не кладёт `PublishReferencesDocumentationFiles=false`). Сборки, которым хватает JIT при первом вызове, исключены из ReadyToRun **двумя**
списками: один exe с ReadyToRun SDK собирает составным, и без `PublishReadyToRunCompositeExclusions`
исключение не действует — до 1.33.0 разборщик так и предкомпилировался (−3,4 МБ после починки).
Готовый файл кладётся в `release/` под именем
`Amarin-Admin-AI-v<версия>-win-x64.exe` и выкладывается вместе с `SHA256SUMS`: без суммы
программа обновление сама не ставит (см. «Обновление ставится только сверенным»).
С 1.26.0 заметки к релизу и `README.md` пишутся **по-английски** — их читают не только
русскоязычные; комментарии в коде и сама памятка остаются русскими. С той же версии релиз
выпускает `.github/workflows/release.yml`: заметки кладутся в
`.github/release-notes/v<версия>.md`, и пуш их в `main` собирает exe на `windows-latest` теми
же флагами, прогоняет тесты (итог — артефакт `test-results`, выпуск он не останавливает) и
создаёт релиз `v<версия>` из `<Version>` в csproj. Если в секретах репозитория есть
`SIGNING_CERT_PFX_BASE64` и `SIGNING_CERT_PASSWORD`, exe подписывается signtool до подсчёта суммы;
`SHA256SUMS` пишется и выкладывается всегда. Повторный запуск той же версии заменяет файлы и
заметки, а не падает. Выпущенный exe не подменяют ради починки — выпускают следующую версию:
кто уже обновился, иначе исправления не получит. Workflow `Tests` запускается вручную и умеет
прогнать любой коммит (`ref`); на раннере GitHub оконные тесты ненадёжны (экран 1024×720,
общий поток интерфейса то не стартует, то умирает), поэтому падения там сверяют с прогоном
прежней версии, а «зелёно» по-прежнему означает зелёный `dotnet test` на настоящей машине.
Workflow `CI` идёт на каждый пуш: сборка с `-warnaserror`, тесты без окон (`Category!=Wpf`;
оконные классы помечены трейтом `WpfCollection.Trait`, наличие метки сторожит
`TestCategoryTests`) и прогон инструментов `--smoke-report` с `continue-on-error` — его таблица
в сводке шага, отказ из-за отсутствующего компонента помечен `SKIP`.

Упавшие тесты CI и выпуск выводят аннотациями (с 1.33.0). Сводку шага, журнал и артефакт GitHub
показывает только после входа, а аннотации видны всем: на странице коммита и через API
`check-runs/<id задания>/annotations` без ключа. Раннер — английская Windows: культура en-US,
кодовая страница ANSI 1252, часовой пояс UTC. Тест, который полагается на русскую машину,
зеленеет здесь и краснеет там. Так остановился первый пуш 1.33.0: тест кодировки писал файл в
1251 и ждал, что программа прочтёт его в 1251. Культуру, кодовую страницу и пояс тест задаёт
явно. Выпуск запускает только пуш, меняющий `.github/release-notes/`, а повтор вручную требует
входа на GitHub.

Версия с пометкой (`<Version>1.29.0-beta.1</Version>`) выходит из `release.yml` предварительной
(`--prerelease`), и её видит только бета-канал. SDK выбрасывает пометку из версии сборки
(`1.29.0.0`), поэтому версия программы читается из `AssemblyInformationalVersion` без хвоста
после «+» (`UpdateChecker.VersionOf`), а сравнивается как `ReleaseVersion` по semver — по одним
числам бета и финальная равны, и человек на бете финальную не получил бы никогда. Заметки
`.github/release-notes/v<версия>.md` вшиты в exe ресурсом (`WhatsNew`, окно «Что нового» —
раз на версию), так что файл заметок должен лежать в репозитории до сборки; нет его — окно
просто не показывается. Текст заметок в окне режется на 20 000 знаков (`UpdateChecker.NotesLimit`).

Версия живёт в двух местах и меняется вместе: `<Version>` в csproj приложения и `Text="v…"` у
`SettingsVersionText` в `UI/Settings/SettingsView.xaml`. В интерфейсе версия берётся из сборки
(`RuntimeContext.AppVersion`), разметка — только заготовка для конструктора. `Amarin.Core.csproj`
своей версии не держит: берёт её из csproj приложения функцией свойства (совпадение сторожит
`ArchitectureTests`), и заметки «Что нового» встраиваются ресурсом в Core — там их читает `WhatsNew`.

Сборка идёт без единого предупреждения. Держите так: любое новое предупреждение — ваш баг.
С 1.30.0 к компилятору добавились анализаторы (`Directory.Build.props` — уровень, `.editorconfig` —
правила поимённо): запечатанные internal-типы, токены отмены до конца цепочки, один
`JsonSerializerOptions` на место вызова, явный `_ =` у отброшенного кода возврата WinAPI, фигурные
скобки, мёртвые закрытые члены. Замороженные зоны (инструменты и их шлюз, прокрутка, лупа)
исключены там же поимённо — категория поимённое правило не перебивает. Обработчики, которые
разметка подключает по имени, анализатор считает мёртвыми, поэтому IDE0051 в `UI/` выключен:
неиспользуемый метод окна ищите глазами. `!` (подавление nullable) в Core не осталось вне
замороженных зон — вместо него `[NotNullWhen]` у Try-методов и проверка образцом.

## Карта проекта

| Где | Что |
|---|---|
| `Amarin Admin AI/Program.cs` | точка входа: профили → тема → экран входа → настройки → службы → окно |
| `Amarin Admin AI/Composition/` | корень композиции: `AppConfiguration` (appsettings, окружение) и `AppComposition.Build` — единственное место, где службы создаются |
| `Amarin Admin AI/UI/` | окна, разметка, темы, отрисовка сообщений |
| `Amarin Admin AI/Computer/` | экран, окна, мышь и клавиатура Windows для оператора (`WindowsComputer`, UI Automation, `SendInput`) |
| `Amarin Admin AI/UI/Settings/` | настройки: оболочка `SettingsView` и страницы (см. «Настройки — 720×520, одиннадцать страниц») |
| `Amarin.Core/` | сборка без WPF: вся логика и инструменты (см. ниже) |
| `ProjectFox/` | лисёнок Роза — сборка `Amarin.Fox` (см. «Лисёнок Роза») |
| `Amarin.AdminAI.Tests/` | тесты; `InternalsVisibleTo` у всех сборок, internal-типы видны |
| `release/` | сборки и заметки к релизам, **в git не попадает** |

`Amarin.Core` — отдельная сборка с 1.30.0, и UseWPF в ней нет: «логика не знает об окне»
сторожит компилятор. Папки — функции, пространства имён — слои (`Amarin.Core`, `Amarin.Tools`),
поэтому перенос файла между папками кода не меняет:

| Папка | Что |
|---|---|
| `Chat/` | движок чата (`ChatEngine`), модели переписки, содержимое для модели, цитаты, варианты, заголовок, сводка, сжатие контекста, инструкции |
| `Turns/` | идущий ход: реестр ходов (`TurnRegistry`), окружение хода (`TurnScopes`), отложенная запись (`ChatPersistQueue`), порядок проверок перед отправкой (`SendPlanner`), `RunningTurn`, `VeniceTurnScope` |
| `ChatList/` | список чатов: папки и метки (`ChatOrganizer`), выбор строк (`ChatSelection`), слепок состава (`ChatListSignature`), перетаскивание (`ChatDrop`), поиск по всем чатам |
| `Agents/` | агент, его хост и реестр, маршрутизатор уровней, разбор аргументов инструментов, MCP, удалённые машины, расписание, «Состояние ПК» |
| `Providers/` | клиент Venice/OpenRouter, каталоги моделей, слоты и ключи, цены, поиск в сети |
| `Spending/` | журнал трат, лимиты (`SpendGuard`, правка — `SpendLimitsEditor`, строки — `SpendPrompts`), остатки ключей |
| `Storage/` | файлы на диске: чаты и вложения, черновики, профили, замки файлов, JSON |
| `Settings/` | `AppSettings` и его хранилище, оформление, сочетания клавиш, интеграция с Windows |
| `Data/` | данные профиля и переезд на другой (`ProfileScope`), архив данных, резервные копии, очистка, разбивка места, «Удалить все данные» |
| `Security/` | шлюз инструментов (`ToolGate`), SynGuard, очередь подтверждений, аудит, шифрование, пароли, подписи, секреты для вырезания (`SecretRegistry`) |
| `Updates/` | проверка и установка обновлений и их автомат (`UpdateMachine`) |
| `Text/` | строки интерфейса (`Loc`, `StringsRu`), формулы, языки кода, перевод интерфейса |
| `Platform/` | журналы производительности и аварий, отчёт об ошибке, фоновая компиляция запуска, `Detached`, открытые окна и сеанс Windows, мелодии (`ChimeSynth`) |
| `Documents/` | чтение Word/Excel/PowerPoint/PDF частями, создание и правка документов (с 1.37.0 и PowerPoint), анализ таблиц (`TableQuery`), диаграммы Excel, `DocumentDigest` для вложений |
| `Media/` | то, что есть только в WinRT, через PowerShell 5.1 (`WinRtScript`): OCR (`LocalOcr`), звук из записи и видео (`MediaAudio`) |
| `Deferred/` | отложенные задачи: модель и сроки (`DeferredClock`), книга (`DeferredBook`), проверка сроков (`DeferredRunner`), команды и условия, Планировщик (`SchtasksDeferredWake`) |
| `Computer/` | управление компьютером мышью (1.36.0): порт `IComputer` и плашка `IComputerStage`, правила `ComputerSafety`, сеанс, правило агенту (`ComputerPrompt`), окно картинок |
| `Browser/` | встроенный браузер агента (1.37.0): порт `IWebBrowser`, `BrowserHub` и сеанс прогона, правила `BrowserSafety`, правила моделям (`BrowserPrompt`); WebView2 — в приложении (`Amarin Admin AI/Browser`) |
| `Tools/` | инструменты, которые видит модель (`ITool`), и защита опасных действий |

Нижние папки — `Storage`, `Providers`, `Settings`, `Platform` — не знают движков (ход, агент,
шлюз, обновление, перенос данных): это сторожит `ArchitectureTests`. Новый файл кладут в папку
своей функции; если он нужен хранилищу или клиенту провайдера, он не должен тянуть за собой
движок.

**Службы собирает один корень — `AppComposition.Build`.** До 1.30.0 граф собирался посреди
`Program.RunWpf`, а тесты переписывали его руками в пяти местах. Теперь `Program` делает только то,
что идёт до профиля (компиляция по профилю, отложенное стирание, конфигурация, профиль, тема,
язык, экран входа, прогрев фона), а всё, что от профиля зависит, — один вызов корня. Свой корень,
а не контейнер: время жизни у служб одно, профиль перекореняется на месте, ошибка зависимости —
ошибка компиляции. Общую на процесс статику (белый список загрузок, отметки MCP для шлюза) ставит
отдельный `ApplyProcessWide` — его зовёт только запуск, поэтому граф собирается в тесте без окна
(`AppCompositionTests` проверяет связи). Данные профиля — `ProfileScope` (Core): окно читает их
через `AppServices`, который только пересылает, а переезд на другой профиль (`UseProfile`)
проверяется без окна. Тестам службы собирает один `UiServices.Build` — урезанный граф без
инструментов и MCP, с настройками в памяти. Новая служба — строка в корне и, если она нужна окну
в тестах, в `UiServices`; пятой ручной сборки заводить не надо.

Крупные классы Core разнесены по partial-файлам по обязанностям: `VeniceClient.*` (очередь
пакетов, аккаунт и модели, учёт трат, медиа, поиск), `ChatEngine.*` (раунд инструментов,
дописанное по ходу, цены, выбор модели, промпты), `ChatStore.*` (опись, вложения, перешифровка).
Новый метод кладут в файл своей обязанности, а не в основной.

`MainWindow` — 3300 строк разметки и 3700 строк кода плюс шесть десятков `partial`-файлов
(`MainWindow.Account.cs`, `.Appearance.cs`, `.Updates.cs`, `.Turns.cs`, `.Language.cs`, …).
Настроек в его разметке нет: они в `UI/Settings`, а в `MainWindow.xaml` от них остался
пустой хост `SettingsOverlay`. Новая страница настроек — свой `UserControl`, не вставка в чужую.

Данные пользователя при работе: `%APPDATA%\Amarin Admin AI` — `settings.json`, `profiles.json`,
`chats/`, `languages/` (переводы интерфейса, общие для всех профилей; поправленное руками
помечено служебной строкой `"$edited"`), `handoff/` (запрос от второго запуска программы). С 1.28.0
в папке профиля ещё: `recipes/<id>.json`, `schedule.json` и журнал прогонов `schedule-runs.jsonl`,
`health.json`, `machines.json` и `mcp.json` (секреты под DPAPI, в архив не едут, как `keys.json`;
с 1.34.0 так же — `provider-keys.json` с ключами новых провайдеров и своими серверами),
`drafts/`, `chats/organize.json`, `chats/search.idx` (индекс поиска, в архив
не едет — собирается заново), `chats/<id>/attachments/`, с 1.35.0 — `fox/state.json` и
`fox/diary.json` (память и дневник Розы, категория архива «Чаты»). Новый вид файла — строка в
`DataBundle.CategoryOf`, `DataUsage` и `ProfileDataWiper`, иначе он молча не уедет в архив или
переживёт «Удалить все данные». Рядом с exe после удачного обновления лежит прошлая версия
`<exe>.previous` (см. «Прошлая версия лежит рядом»). Профиль по умолчанию указывает на корень этой папки, остальные —
на `profiles/<id>`; менять эту раскладку нельзя, иначе у людей пропадут старые переписки.

## Ловушки, на которых уже спотыкались

**Ходов чата несколько, и состояние хода — на ходе.** Реестр — `TurnRegistry` (`Amarin.Core/Turns`,
окно держит его как `Turns`), по одному `RunningTurn` на чат, до трёх сразу (`TurnRegistry.MaxParallel`);
отказ начать ход — ответ `TurnStart`, а не исключение. Что проверять перед ходом и в каком порядке
(ключ, `/agent` с вложениями, лимит ходов — **до** очистки поля), решает `SendPlanner`: в 1.29.0
отказ давал сам запуск хода, и сообщение пропадало вместе с вложениями. Ни `ChatEngine`, ни `VeniceClient` состояния хода
больше не держат: модель, размышление и накопленная цена живут в `VeniceTurnContext`
(`VeniceTurnScope` — ambient по образцу `AgentRunScope`). Новый код, которому нужна «текущая
модель» или «сколько потрачено», берёт их оттуда, а не у клиента: поле клиента общее, и два
хода перетопчут друг друга. `SetActiveModel` поэтому и удалён. Открывая чат, берите
`FindTurn(id)?.Session` раньше, чем `ChatStore.TryLoad(id)` — иначе движок продолжит писать в
свой объект, а на экране окажется застывшая копия с диска.

**Строки интерфейса — словарь, а не литералы.** Разметка читает их через
`{DynamicResource S.Ключ}`, код — через `Loc.Get`/`Loc.Format`. Источник истины —
`UI/Lang/Strings.ru.xaml`; `Strings.en.xaml` обязан иметь ровно те же ключи, а `Amarin.Core/Text/StringsRu.cs`
— его копия для кода и для тестов без интерфейса. Все три сверяет `LocalizationTests`, так что
новую подпись добавляют во все три сразу. Словарь занимает **слот 4**
`Application.Resources.MergedDictionaries` — слот 3 сдвигать нельзя, в него по номеру пишет
`AppearanceManager`. Перенос строки внутри значения пишется `&#10;` и только вместе с
`xml:space="preserve"`: иначе XAML схлопнет его в пробел. Ведущих и хвостовых пробелов в
значениях быть не должно — XAML их срежет, а `StringsRu` сохранит, и тест разойдётся.
`ChatTitle.Default` — не подпись, а маркер на диске; переводится только его показ
(`MainWindow.DisplayTitle`). Русские литералы в коде ловит `SourceLiteralTests` (без окна, идёт
в CI): папки `Updates`, `Data`, `ChatList`, `Turns` проверяются целиком, остальное — списком
файлов. Промпты и строки, которые читает модель, пишутся по-русски законно — поэтому файл с
подписями для человека в папке вроде `Chat/` вносят в список поимённо.

С 1.32.0 в значениях строк нет длинного «—» и среднего «–» тире: человек их не печатает, и это
первая примета текста от модели. На их месте дефис с пробелами, двоеточие или другая фраза;
сторожит `TypographyTests` (заодно README и заметки текущей версии). Машинный перевод интерфейса
получает то же правило в промпте, а приём ответа (`LanguageTranslator.Accept`) и чтение
сохранённого перевода (`UserLanguageStore.ToDictionary`) меняют тире через
`TextTypography.PlainDashes`; строки, поправленные руками (`$edited`), не трогаются. Править
строки пачкой удобно скриптом, который заменяет значение на месте: словари не отсортированы
целиком, и вставка «по алфавиту» плодит дубликаты ключей.

**До первого кадра — только то, что на нём видно.** С 1.25.0 `AttachServices` успевает ещё и
покрасить фон (`ApplyAppearance(save: false)`), а настройки до первого кадра не строятся вовсе:
их страницы собирает прогрев в простое (см. «Настройки строятся после первого кадра»). Это
безопасно ровно потому, что **контролы страниц настроек нигде не читаются как состояние** —
каждый живёт только в своём `*_Changed` под `_settingsUiLoading`, а правда лежит в `AppSettings`.
Заведёте настройку, которую кто-то читает прямо с контрола, — сломаете запуск, а не эту страницу.
Самой первой строкой `RunWpf` включается фоновая компиляция по профилю (`StartupJit`,
multicore JIT): профиль покрывает только то, что скомпилировано после него, поэтому раньше этой
строки ничего тяжёлого не ставьте. Профиль — кэш машины в `%LOCALAPPDATA%\AmarinAdminAI\jit`,
по файлу на версию, в архив данных не едет. Там же рядом: картинки гайда (`GuideShot`)
распаковываются не в `InitializeComponent`, а по первому `IsVisible`, и с `DecodePixelWidth` — иначе это сорок мегабайт пикселей на потоке
интерфейса ради гайда «Как начать работу», который в этом запуске могут и не открыть. Замеры —
`app_start`, `main_window_ctor` и `settings_*` в `PerfLog` (`AMARIN_PERF_LOG=1`).

**`Show()` выводит окно раньше, чем оно нарисовано.** `Loaded`, раскладка и первый кадр идут
внутри самого `Show()`, после `ShowWindow`, и всё это время Windows показывала на месте окна
белый прямоугольник — на холодном запуске полсекунды, под отладчиком VS секунды. С 1.30.0 до
первого кадра на `WM_ERASEBKGND` отвечает `WindowFirstPaint`: заливка цветом `Bg.Window`, после
`ContentRendered` перехватчик снимается (дальше он закрашивал бы нарисованное). А список чатов к
первому кадру строит только то, что видно в колонке (`RefreshChatListFirstScreen`), хвост
дописывает обычный `RefreshChatList` сразу за кадром: раньше раскладка всех строк — её
синхронно запускал ещё и `ScrollToEnd` поля ввода — держала первый кадр треть секунды на трёхстах
чатах. Новое в `OnWindowLoaded`, чего на первом кадре не видно, — туда же, за кадр. Холодный
запуск по шагам меряет `StartupBenchTests` (`AMARIN_STARTUP_BENCH`, отдельный процесс, Release):
конструктор окна — 0,47 с холодным и 0,12 с прогретым, это разбор самой разметки; до выноса
настроек было 0,83 и 0,4 — больше половины разметки занимала панель, которой на первом кадре не видно.

**Фон-картинка готовится заранее и лежит готовой на диске.** `AppearanceImageCache` считает
обои на рабочем потоке, а показывается тем временем градиент — и на запуске это читалось как
«сначала загрузилась затычка». Теперь `Program` зовёт `Prewarm` ещё до `new MainWindow()`, пока
WPF разбирает разметку, а результат кладётся рядом с картинкой файлом `background.<отпечаток>.cache.png`
(его же не берёт в архив `DataBundle.CategoryOf` — производное человеку пересылать незачем).
Путь к картинке разрешает `AppearanceImageCache.ResolvePath`, и второй копии этого правила быть
не должно: разойдись они, прогрев считал бы под одним ключом, а окно спрашивало бы под другим.
Округление в `Peek` обязано повторять `Load` до знака — пока его там не было, ключ от ползунка
(`1.1506…`) не совпадал с положенным (`1.15`) **никогда**. Опоздавшая картинка не подменяется
рывком, а проявляется отдельным слоем `_photo`.

**Ценник правят у одного сообщения, а не у всего чата.** Сводка и заголовок приезжают брошенными
задачами и приписывают свою цену уже закрытому ответу. Раньше ради этого звали `RenderSession`,
то есть сносили и строили заново всю ленту, — а она первой строкой сбрасывает лупу, и
приближение слетало через секунду после каждого ответа. Теперь пузырь пересобирает
`RefreshMessageView(id)` (`MainWindow.Messages.cs`), а `ChatTitleCost.Book` отдаёт само
переоценённое сообщение, чтобы было что ему передать. Перерисовкам того же чата, где содержимое
не менялось (формат даты, смена языка), полагается `RebuildTranscript(resetZoom: false)`;
`RenderSession()` остаётся входом «показать другой чат» и лупу сбрасывает. Отдельным именем, а не
необязательным параметром: `RenderSession` зовут тесты через отражение, а `MethodBase.Invoke`
значений по умолчанию не подставляет. С 1.26.0 лупу сбрасывает **только** смена чата: открытие
настроек её не трогает, а правка, удаление и перегенерация зовут `ReconcileTranscript(id)` —
он снимает пузыри вырезанных сообщений и пересобирает изменённый, не строя ленту заново.
Двойной клик сбрасывает лупу лишь на пустом месте ленты, не на кнопке, ссылке или тексте.

**Горячие клавиши разбираются до `ShouldKeepKeyboardFocus`.** Тот уступает событие полю ввода при
любом Ctrl или Alt, а сочетание без модификатора завести нельзя (голая буква перехватывалась бы
прямо во время набора) — значит ниже той строки ни одно сочетание не дожило бы. Список действий
один на программу (`HotkeyMap.All`), назначения лежат словарём `AppSettings.Hotkeys`, и
отсутствующее действие берёт заводское: старый `settings.json` читается без миграции, а сброс
просто убирает запись. Запись сочетания без WPF живёт в `Settings/HotkeyMap`, перевод в `Key` и
`ModifierKeys` — в `UI/Hotkeys`; поле записи гасит **все** нажатия, пока пишет, иначе назначаемое
сочетание само же и срабатывало бы в момент настройки. С 1.28.0 «Новый чат» — Ctrl+N (Ctrl+F
везде значит «найти»). Нажатие разбирается по `HotkeyMap.Effective`, а не `Gesture`: явное
назначение побеждает заводское, и заводской дубль чужого явного назначения не срабатывает — иначе
смена заводского отняла бы клавишу у того, кто сам отдал её другому действию («Новый чат» стоит
в списке первым и никогда не отказывается). С 1.32.0 вместо Ctrl или Alt годится Shift, но только
с клавишей, которая не печатает текст (`HotkeyMap.IsCommandKey`: Delete, Insert, F1-F24) — так
заведено Shift+Del. «Выделить все чаты» (Ctrl+A) и «Удалить чаты» (Shift+Del) срабатывают, лишь
пока клавиатура у главного окна (`ChatListKeysAvailable`: нет блокировки, `ChatBlocked` и
открытых слоёв поверх `ScaledRoot`), и уступают тексту: Ctrl+A выделяет текст в поле с текстом и
в блоке кода (`TextOwnsSelectAll`, метка `CodeBlockView.IsCode`), Shift+Del вырезает выделенное в
поле (`TextOwnsCut`). В пустом поле ввода Ctrl+A выделяет чаты.

**Цитата живёт рядом с текстом, а не в нём.** «Ответить» на выделенное в ответе модели кладёт
фрагмент в `ChatDisplayMessage.Quotes` (`MessageQuote`), а `Text` остаётся тем, что человек
написал: его читают маршрутизатор «Авто», заголовок, сводка и правка, и слова ассистента там
были бы чужими. Модели цитаты уходят английским блоком перед сообщением (`ChatQuotes.Wrap`),
который объясняет себя сам — системные промпты для этого не трогаются. Источник в блоке назван
«последним ответом» или началом его текста, **но не номером**: отменённые ответы в историю
модели не попадают, раунды инструментов добавляют свои записи, и «ответ №3» врал бы. Сообщение
человека для модели собирает один `ChatContent.ForUser` — и отправка, и правка
(`ReplaceUserText`), и пересборка после удаления хода; заведёте четвёртое место — соберите
через него же, иначе цитаты или вложения выпадут молча, как уже выпадали документы.
`Selection.Text` теряет всё, что нарисовано элементом (код, формулы), поэтому `ChatMarkdown`
вешает на такие элементы исходник (`QuoteSelection.Source`), а текст выделения собирает
`QuoteSelection.ExtractText`. Своё меню по правому клику лента открывает только потому, что у
боксов стоит **локальный** `ContextMenu = null`: без него редактор текста сам показывает
системное меню и гасит событие.

**У модалок содержимое лежит в `Grid`, а не в `StackPanel`.** `StackPanel` границу в своём
направлении не соблюдает: меряет детей бесконечностью и раскладывает подряд на полную желаемую
высоту. У окна подтверждения опасного действия ряд «Да»/«Нет» стоял последним и на длинном
разъяснении с раскрытыми экспандерами уезжал ниже кромки карточки — то есть последний экран перед
запуском скрипта становился непригодным. Правильная форма — та, что у `JournalOverlay`: строки
`Auto` под заголовок и подвал, строка `*` под прокручиваемое тело, и всё, что может вырасти,
внутри неё.

**Окно создаётся до `Show()`.** `AttachServices` → `UiScale.Apply` → `EnsureHandle()`. Поэтому
`SourceInitialized` случается раньше, чем дерево визуалов привязано к источнику, и
`PresentationSource.FromVisual(window)` в этот момент возвращает `null`. Перехватчики сообщений
ставьте через `HwndSource.FromHwnd(new WindowInteropHelper(window).Handle)` — см.
`WindowMaximizeFix.TryHook`. Из-за этой мелочи разворот окна молча уезжал за края экрана.

**Главное окно — `WindowStyle="SingleBorderWindow"`, не `ToolWindow`.** Свой заголовок рисует
`WindowChrome`, стиль же решает, кем окно считает Windows. С `ToolWindow` (`WS_EX_TOOLWINDOW`)
до 1.27.0 его не было в Alt+Tab, кнопка на панели задач появлялась лишь после первого фокуса,
а сворачивание чужой программы уносило окно следом. Сторожит `MainWindowStyleTests`.
Побочный эффект смены стиля — Windows 11 скругляет обычное окно крупнее, чем «инструмент»,
поэтому углы задаются явно: `AppSettings.WindowCorners` → `WindowCornerStyle.Apply`
(`DWMWA_WINDOW_CORNER_PREFERENCE`), заводское — маленькое скругление, как было. Своего радиуса
DWM не принимает; `WindowChrome.CornerRadius` на вид окна не влияет. И второй эффект: развёрнутое
обычное окно Windows всё равно выносит на невидимую рамку за края экрана, хотя прямоугольник
правится в `WM_GETMINMAXINFO`/`WM_WINDOWPOSCHANGING`. Поэтому у развёрнутого окна
`WindowMaximizeFix` отвечает и на `WM_NCCALCSIZE`: клиентская область — окно, обрезанное по
рабочей области (`ClientAreaFor`), где бы ни легла рамка. Ответ наш лишь потому, что перехватчик
ставится позже, чем у `WindowChrome`, а `HwndSource` зовёт последний добавленный первым; тест
`A_maximized_window_draws_only_inside_the_work_area_whatever_its_frame` шлёт сообщение настоящему
окну и заметит, если порядок сменится. Запасной рубеж — `UpdateContentInset`: меряет клиентскую
область по факту и отодвигает корневой элемент на вылезшую часть (`Overhang`).

**Масштаб интерфейса — это подделанный DPI.** `UiScale` шлёт окну синтетический `WM_DPICHANGED`
с нужным значением, а не масштабирует разметку. Всё, что считает размеры в пикселях или ловит
сообщения окна, обязано это учитывать.

**`WM_GETMINMAXINFO` перехватывает только `WindowMaximizeFix`.** В `WindowMoveBehavior` жил
второй такой обработчик — он дрался за то же сообщение и врал с координатами на втором мониторе;
его удалили. От `WindowMoveBehavior` осталось перетаскивание окна, и заводить там второй
перехватчик заново не нужно.

**Выпадашки регистрируются в `PopupManager`.** `StaysOpen="False"` здесь не работает: он гасит
попап тем же нажатием, которым `ClickMode="Press"` его открывает, и не видит кликов в чужом окне
попапа — они копятся на экране. Новый `Popup` — строкой `PopupManager.Register(popup, toggle)`
сразу после `InitializeComponent`.

**`SmoothScroll` слушает туннелирующее событие.** Хук сидит на `PreviewMouseWheel`, иначе своим
`OnMouseWheel` виджет успел бы дёрнуться рывком до инерции. Плата за это — событие приходит
сверху вниз: включённый на странице настроек скролл забирал колесо раньше, чем его увидят
вложенный список, поле промпта и раскрытая выпадашка, и вместо них листалась страница. Поэтому
`OnWheel` сперва смотрит, кому событие адресовано (`AimedDeeper`), и уступает всему, чему вправду
есть что прокрутить, — а на собственном краю отдаёт колесо наружу сам (`HandOver`), потому что
пузырьковый `MouseWheel` до предка не дошёл бы: его забирает `OnMouseWheel` этого же
`ScrollViewer`. Включая скролл на новом контейнере, проверяйте, что внутри него нет ничего
своего прокручиваемого.

У того же хука ещё два умения, и оба на его физике, а не своей. `SmoothScroll.DragScroll` —
листать зажатой кнопкой (страницы настроек; в ленте чата кнопка занята выделением и лупой, в
колонке чатов — перетаскиванием чатов, см. ниже): нажатие не забирается, жестом оно становится за порогом сдвига, и тогда
хук отбирает мышь у кнопки под курсором — клика на отпускании не будет. Свой жест не отдают
текст, ползунки, выпадашки, кнопки с `ClickMode="Press"` и вложенные прокручиваемые списки.
Взведённый жест гасит всплывающее нажатие — иначе его забрал бы `TitleBar_MouseDown` на
перетаскивание окна. `SmoothScroll.GlideTo` — доезд к краю для стрелок чата: цель
пересчитывается каждый кадр (низ растёт при стриминге), колесо перехватывает доезд, а лента
на это время не достраивает сообщения — строит по прибытии.

Пока список едет сам (инерция колеса, доезд), хук держит `SmoothScroll.IsInMotion` и поднимает
`MotionChangedEvent`. Колонка чатов по нему ставит строкам `ChatRowState.Scrolling`, и шаблон
строки на это время не откликается на наведение — ни подсветкой, ни кнопкой «⋯», ни подсказкой
(1.32.0). Под инерцией строки проезжают под неподвижной мышью, и каждая раскладывала заново
заголовок с многоточием и кнопку: над строками прокрутка дёргалась, а у полосы шла гладко, — замер
показал вдвое больше работы окна. Новый список, у строк которого наведение меняет раскладку, берёт
тот же приём; наведение, которое только перекрашивает, дёшево и его можно оставить.

Третье умение хука (1.33.0) — `SmoothScroll.PanScroll`, автопрокрутка средней кнопкой в ленте,
колонке чатов и настройках: метка-кружок на месте нажатия, скорость от расстояния до неё (мягко
у метки, экспоненциально дальше; в 400 точках от метки — предельная, с которой **весь список
проходится за 0,6 с**, какой бы длины он ни был, но не меньше 50 000 точек/с; шаг — настоящее
время кадра до 0,25 с, иначе на тяжёлом чате в пять кадров в секунду скорость резалась бы вдвое).
Постоянный потолок был ошибкой: чат на сотни тысяч точек листался до верха много секунд.
Не путать с настройкой «Автопрокрутка чата» — до 1.33.0 оно и называлось `AutoScroll`. Клавиши,
колесо и отпускание кнопки разбирают **классовые** обработчики `Window`
(`EventManager.RegisterClassHandler`): они срабатывают раньше `Window_PreviewKeyDown`, и только
поэтому Esc под меткой снимает автопрокрутку, а не останавливает ответ (так было в первой
версии, и прокрутка после Ctrl+Tab писала в чужой чат). Правая кнопка заканчивает её без
контекстного меню, Ctrl+колесо — тоже; при зажатой левой или правой она не начинается (там
выделение, рамка, перетаскивание, лупа). Пока метка движется, `IsInMotion` поднят и лента не
достраивает сообщения; метка в мёртвой зоне движением не считается.

**Чаты перетаскиваются жестом окна, а не OLE.** С 1.29.0 зажатая кнопка в колонке чатов несёт
чат в папку, в закреплённые, в общий список или в архив (`ChatListDrag`). `DoDragDrop` не
годится: он будил бы оверлей вложений и разворот композера, которые ждут файлов снаружи. Куда
упадёт чат, раскладка пишет каждой строке и заголовку в `ChatRowState.DropTarget`; что
поменять, решает чистая `ChatDrop.Plan` — брошенное в папку снимает закрепление (иначе чат в
папке не показался бы), закреплённое сохраняет папку. Пока жест идёт, `RefreshChatList` не
пересобирает список (`RefreshPending`) — пересборка вырвала бы строку из-под курсора.

**Достройка ленты стоит, пока лента в движении.** Фоновая дорисовка большого чата строит
сообщения выше видимого и сдвигает ленту под якорь; под жестом лупы или инерцией у смещения
вышло бы два хозяина, и приближение дёргалось и прыгало (`TranscriptInMotion`). Конец жеста
лупы будит дорисовку сам (`OnChatZoomSettled`), инерцию — короткий таймер. Порция дорисовки
меряется временем, а не числом сообщений, а место под непостроенное прикидывает
`MessageHeightEstimate` по разметке: чем точнее прикидка, тем меньше сдвиг при постройке.

**Пока окно меняет размер, лента перекладывает только видимое.** Каждое построенное сообщение —
`RichTextBox` со своим документом, и до 1.30.0 смена ширины перекладывала их все: на чате в 1200
сообщений шаг перетаскивания края стоил секунду процессора, разворот — столько же, и Windows всё
это время показывала на месте новой части окна чёрное. Жест (край окна между `WM_ENTERSIZEMOVE` и
`WM_EXITSIZEMOVE`, разворот и возврат по смене `IsZoomed`) узнаёт `WindowResizeWatch` — он только
слушает и ставится после `WindowMaximizeFix`, поэтому слышит `WM_WINDOWPOSCHANGING` первым, до
раскладки нового размера. На начале жеста всё вне живой полосы (`TranscriptReflow.LiveBand`: у
низа — экран над видимым, при чтении середины — экран под ним) замораживается:
`ChatMessageHost.Freeze` отдаёт сообщению ту же ширину, что в прошлый раз, и WPF пропускает его
раскладку целиком. Высота замороженного не меняется, поэтому место чтения не уезжает. После жеста
замороженное отпускает та же фоновая очередь, что достраивает ленту (`ThawNextChunk` раньше
достройки, с её якорем и паузой под лупой и инерцией). Поддельный `WM_DPICHANGED` из `UiScale`
жестом не считается. Высоты сообщений запоминаются вместе с шириной:
высота при другой ширине уже не та. Новый код, который строит или заменяет вьюшку сообщения,
обязан помнить, что хост может быть заморожен, — `Fill` на замороженном мерит новое содержимое по
старой ширине до отпускания, и это правильно.

Ширину ленты меняет не только окно. Ручка боковой панели (`SidebarGrip`) и её сворачивание
(Ctrl+B) до 1.32.0 перекладывали все построенные сообщения на каждом шаге, и окно замирало на
секунды: шаг ручки на чате в 1200 сообщений стоил 1,5 с, теперь около 20 мс. Поэтому заморозка — счётчик
жестов `BeginTranscriptReflow(reach)`/`EndTranscriptReflow()` (`MainWindow.Resize.cs`): окно,
ручка (`DragStarted`/`DragCompleted`) и разовая смена ширины (`ReflowTranscriptOnce`, через неё
идёт `SetSidebarCollapsed`) зовут одну пару, а конец отпускается через `ContextIdle`, после
последней раскладки. Новое место, которое меняет ширину колонки ленты, берёт ту же пару, иначе
оно вернёт секундный фриз.

**Список чатов сверяется, а не пересобирается.** До 1.30.0 любое изменение состава — раскрытие
папки, переименование, новый чат — сносило панель и строило каждую строку заново (щелчок по папке
на 300 чатах — 120 мс работы окна). Теперь `RenderChatListNodes` сверяет снимок прежней раскладки
с новой (`ChatListPatch`, Core): строка, у которой не поменялось ничего из того, из чего она
строится (штамп), остаётся тем же элементом. Сверка идёт **со снимком** (`ChatListShown`), а не с
прежними узлами: запись описи хранилище правит на месте, и сверка с живым объектом сочла бы
переименованную строку прежней. Полоса карточки, раздел для броска, признаки строки и то, свёрнута
ли папка, в штамп не входят — их ставит на месте `PlaceNodes`; заголовок папки переживает
обновления, поэтому щелчок и меню берут папку из `Tag` в момент нажатия. Раскрытие и свёртывание
идут высотой и прозрачностью (`UiMotion.Grow`/`Shrink`, шеврон — `UiMotion.Turn`, всё гасится
галкой «Анимации»); последняя строка начинает и заканчивает не с нуля, а с разницы между карточкой
в одну строку и верхом раскрытой, поэтому колонка не прыгает. Уходящая строка теряет id в `Tag` и
не берёт мышь — выбор, Ctrl+Tab и перетаскивание её не видят; `ChatListDrag.Starting` доводит
ход строк до конца раньше, чем жест снимет их положения. Всё, что занимает панель своим (выдача
поиска по тексту), зовёт `ForgetChatListRows`.

**Рамка выделения: третий жест колонки чатов.** С 1.32.0 нажатие на строке чата начинает
перетаскивание (`ChatListDrag`), на пустом месте, подписи группы или заголовке папки и архива —
рамку (`ChatListMarquee`), а заголовок окна по-прежнему тянет окно. Рамка не берёт строки чатов,
кнопки внутри строк, полосу прокрутки и поля ввода; у `SideBarScrollViewer` прозрачный фон, иначе
нажатие ниже списка до него не доходит. Выбор живёт в `ChatSelection` (Core): кроме чатов там
«захваченные» папки, и папка в выборе значит все её чаты, в том числе в свёрнутой. Состав папок
и архива для выбора считает `ChatListLayout.Members` по тем же правилам, что `Build`; разойдутся —
рамка и Ctrl+A выберут не то, что видно (сверяет `ChatListModelTests`). Пока рамка идёт,
`RefreshChatList` ждёт (`_chatListRefreshPending`), а Esc возвращает выбор, который был до неё.
Ни рамки, ни состава папок нет на пути запуска: рамку создаёт первое нажатие в колонке
(`Marquee`, обработчик `SideBarScrollViewer_FirstPress` передаёт ей это нажатие), а состав
считается при первом вопросе после пересборки (`ChatListMembersNow`); при пустом выборе
заголовки гаснут без него. В конструкторе окна и на каждой пересборке они стоили холодному
запуску около 8 мс — новое для колонки заводят так же, по первому делу.
Меню чата одно на один чат и на выбор (`OpenChatsMenu`, правый щелчок и «⋯»), пункты собирает
`AppMenu` — его же берёт страница ключей, своих стилей меню не заводят. Полосы кнопок над
списком для выбора нет (убрана по просьбе человека: дублировала меню и сдвигала список); с
клавиатуры то же меню открывает клавиша меню на колонке (`SideBarScrollViewer_ContextMenuOpening`).
Выбор сверяется с живыми чатами и папками на каждой пересборке списка (`PruneChatSelection`).
Нажатие в ленте, в поле ввода и на кнопках боковой панели вне списка снимает выбор
(`ClearSelectionOnPressElsewhere`); пустое место колонки — дело рамки (с Ctrl она добавляет к
выбору, и снять его на нажатии было бы рано), а заголовок окна, край панели и слои поверх окна
выбор не трогают. Предков источника нажатия ищут через `ParentOf`, а не `VisualTreeHelper`: в
ленте нажатие приходит от `Run`, у которого визуального родителя нет, и тот бросает. Пакетное удаление идёт
`ChatStore.DeleteMany` с событием `DeletedMany`: одна запись описи и раскладки на пакет, а не на
каждый чат. Код «Поделиться» на несколько чатов начинается с `AMRN2:` (`ChatShareCodec.EncodeMany`)
и прежними версиями не читается; код одного чата остался `AMRN1:`.

**Оверлей заслоняет чат рамкой, а не флагом.** Вопрос об опасном действии, уведомление, журнал,
«Состояние ПК» и прочие оверлеи ставят `ChatBlocked` — видимость прозрачной рамки `ChatShield`
поверх ленты и композера. До 1.30.0 они переключали `Chat.IsHitTestVisible`, а это свойство (как и
`IsEnabled`) наследуется: WPF обходил всё дерево ленты на открытии и на закрытии, на чате в 1200
сообщений по 45 мс. Не переключайте такие свойства у `Chat` и его предков ради блокировки.

**И ключ, и адрес едут на запросе, а не на клиенте.** Раньше `VeniceClient` ставил
`Authorization: Bearer` на `DefaultRequestHeaders` общего `HttpClient`, и выходило две беды сразу:
клиент нёс ключ в любой запрос, куда бы тот ни шёл (GitHub отвечал 401, а ключ уезжал на
посторонний сервер), а присваивание через `??=` намертво запоминало первый ключ — сменить его
у живого клиента было нельзя. Ровно то же было с `BaseAddress`. Теперь оба ставит
`VeniceClient.Request` на каждый `HttpRequestMessage`, а пару «ключ + провайдер» он берёт из
`ApiKeyProvider` — одного на все копии `AgentOptions`. Новый запрос собирают только через
`Request`, иначе он уйдёт без ключа и не туда. С 1.23.0 ключ едет ещё и параметром: у путей
общего клиента (`CreateChatCompletionAsync`, `StreamChatCompletionAsync`, `ListTextModelsAsync`,
`SearchWebAsync`) есть `ApiCredential? credential`, а у копий настроек под слот — поле
`AgentOptions.Binding`. Пусто и там, и там — платим выбранным ключом, как раньше. Правило про чужих адресатов остаётся в силе:
свой клиент через `HttpClients.Create`, у них разные таймауты, своё представление и свой счёт
потраченного (`RequestCost`). С 1.34.0 `ApiCredential` несёт и адрес своего сервера
(`ProviderEndpoint`), а `Request` предъявляет ключ так, как ждёт сервер: Bearer; Anthropic —
`x-api-key` и `anthropic-version`; свой сервер — оба заголовка (перепродавцы берут ключ как придётся).
Адрес берётся из учётных данных (`EndpointFor`), и у провайдера без адреса запрос не уходит вовсе:
прежде всё, что не OpenRouter, получало адрес Venice. Открытый каталог цен OpenRouter
(`ModelPriceBook`) ходит своим клиентом без ключа — ключ туда уезжать не должен.

**Провайдера задаёт модель, а не ключ.** С 1.23.0 провайдеры работают одновременно: у каждого
из десяти слотов своя модель, а провайдер читается из приставки её идентификатора. С 1.34.0
`LlmProvider` — не перечисление, а значение с текстовым `Id`: дюжина встроенных (Venice,
OpenRouter, OpenAI, Anthropic, Google, xAI, DeepSeek, Kimi, Mistral, Z.ai, Qwen, Groq) и свои
серверы `custom-<6 hex>`. `default` — Venice, как у перечисления; в JSON пишутся те же строки, что
писал конвертер перечислений (`venice`, `openRouter`), читаются и числа 0/1, незнакомый `Id` не
бросает. Всё, чем провайдеры отличаются, — свойства `ProviderSpec` (протокол, диалект тела
запроса, как сказать о размышлении, откуда остаток, есть ли цена, картинки, поиск, очередь),
а не ветка «если Venice, иначе OpenRouter»: такой ветки в коде больше нет, и заводить её
нельзя. Незнакомому провайдеру `ProviderSpec.For` отдаёт описание без адреса — запрос к нему не
уйдёт. Список провайдеров в интерфейсе — `ApiKeyProvider.Providers` (встроенные и свои серверы с
ключами), а не `ProviderSpec.All`. Модели хранятся с приставкой — `openrouter:anthropic/…`,
`anthropic:claude-…`, `custom-a1b2c3:…`. Идентификаторы Venice остались голыми намеренно:
`settings.json`, `keys.json` и все переписки людей читаются без миграции. Разбирают приставку
только через `ModelRef` — разрез по **первому** двоеточию, потому что у OpenRouter бывают
варианты вида `…-sonnet:thinking`, и по последнему двоеточию запрос ушёл бы к другой модели. Что на
провод уходит без приставки — `ModelRef.Bare`; что показывается человеку — тоже без неё
(`VeniceModelCatalog.GetDisplayName`, `GetLogoResourceKey`). Тело запроса собирает `BuildPayload`
по диалекту: у OpenRouter нет `venice_parameters`, зато обязателен `usage: {include: true}` — без
него он не сообщает цену; у прочих OpenAI-совместимых — голое тело без температуры, где модель её
не берёт, а на 400 о необязательном поле — один повтор без него (`Relaxed`). Anthropic говорит
своим протоколом (см. ниже). Чего нет ни у кого, кроме Venice: рисования картинок и чтения
страниц — они ходят в Venice **сохранённым** ключом Venice (`ApiKeyProvider.VeniceCredential`), а
без него отказывают строкой, которую читает модель. Поиск в интернете есть у Venice и OpenRouter;
ход у провайдера без поиска ищет через них (`SearchElsewhere`), а закрепить поиск можно только за
ними. Цепочки замены при перегрузке (`VeniceModelFallback`) — только у Venice и OpenRouter, а в
чате — только под «Авто» (1.36.0): модель, выбранную человеком руками, ход не меняет
(`StreamChatCompletionAsync(…, fallback: false)`), перегрузка кончается строкой
`S.Provider.ModelOverloaded`. Прежде замена шла молча, и на месте выбранной модели отвечала
тяжёлая голова цепочки.

**Anthropic — свой адаптер Messages API, а не OpenAI-совместимый путь.** `AnthropicMessages`
переводит запрос (системное — наверх, роли склеиваются, результаты инструментов — блоками
`tool_result` одним сообщением, картинки и PDF — блоками) и поток (`AnthropicStream`) в те же
`ChatCompletionChunk`, поэтому ниже по течению никто про Anthropic не знает. Размышление решается
по возможностям модели из `/v1/models` (`capabilities.thinking.types`, `effort`): включено —
`adaptive` и `output_config.effort`; выключено — `disabled`, `between_tools` или уровень `low`, что
модель принимает. Подписанные блоки размышления возвращаются только текущего раунда
инструментов: они лежат на сообщении в `ChatMessage.ReplayBlocks` с `[JsonIgnore]` — в файлы и в
тело OpenAI-совместимого запроса не попадают, а их обязаны переносить все копии сообщения
(`ChatMessageCloner`, `ApiContextLimiter`, `ContextHygiene`). Подпись привязана ко всему, что
стоит перед блоком, а гигиена контекста и ограничитель меняют раннюю часть, поэтому официальному
API уходит бета `thinking-binding-controls-2026-08-01` с `drop_block` — устаревший блок сервер
отбрасывает сам, а не отвечает 400; своему серверу этот заголовок не шлётся. Ограничитель снимает
старые вложения только **до** последнего хода человека. История с вызовами без инструментов в
запросе — те же инструменты с `tool_choice: none`; отказ модели (`stop_reason: refusal`) —
понятная строка, а не пустой ответ, который ушёл бы на повтор.

**Ключи новых провайдеров — в `provider-keys.json`, ради отката.** «Вернуть v…» ставит 1.33, а
та читает провайдера ключа перечислением и, встретив незнакомое имя, считает весь `keys.json`
повреждённым — пропали бы и ключи Venice. Поэтому в `keys.json` пишутся только ключи Venice и
OpenRouter (`ProviderSpec.IsLegacy`), а ключи остальных и описания своих серверов
(`CustomEndpoint`) — в соседний файл под тем же DPAPI. Файл зарегистрирован везде, где
`keys.json`: `DataBundle.CategoryOf` (в архив не едет), `ProfileDataWiper`, `SensitivePaths`
(инструментам модели его не прочесть), вырезание секретов. Новый файл с ключами — строка во всех
четырёх местах. Переменные окружения читаются только прежние две: `OPENAI_API_KEY`, поставленный
для другой программы, молча платил бы за этот чат.

**Свой сервер — провайдер по адресу.** Окно ключа (`KeyAddDialog`, создаётся при первом
открытии) пробует адрес (`ProbeServerAsync`): корень API с `/v1` и без, протоколы — пустым телом
(400/422 — «есть», 404 — «нет»), модель при этом не запускается. https обязателен, кроме этого
компьютера. Claude у сервера с обоими протоколами идёт родным протоколом, остальное —
OpenAI-совместимым. Лимит токенов — поле ключа, а не сервера (у одного сервера пакеты разные):
его задают в меню ключа, а расход считает `SpendLedger.TokensUsed` — счёт программы, сервер
может списывать с коэффициентом модели. Ключ с лимитом в сумму долларов не входит: перепродавцы
пишут токены в поля остатка. Ключи без остатка в долларах `BalanceBook` не опрашивает после каждого
ответа (`MarkSilent`, `ReportsDollars`).

**У каждого слота свой ключ.** Выбор слота — это пара `ModelBinding(ModelId, KeyId)`. Модели
лежат по-прежнему плоскими полями `AppSettings`, ключи — одним словарём `ModelKeys` (имя слота →
`Id` ключа); пустой `KeyId` значит «ключ по умолчанию для провайдера этой модели», поэтому
`settings.json` и переписки прежних версий читаются без миграции. Читают и пишут пару только
через `ModelSlots.Binding`/`WriteBinding`, разрешают ключ — через `ApiKeyProvider.CredentialFor`:
назначенный ключ принимается, лишь если он того же провайдера, что и модель, иначе секрет уехал
бы на чужой сервер. Список слотов один на программу (`ModelSlots.All`): второй разошёлся бы
с ним молча. Зашитый в коде идентификатор Venice как «последняя соломинка» оборачивают
в `ModelSlotDefaults.LastResort`, иначе на ключе OpenRouter он уйдёт в четырёхсотку.
Лечение выбора (`ModelSlotHealing`, Core; окно только зовёт его из
`HealUnusableModelSelections`) сверяет слот с каталогом **его** провайдера и только если тот
загружен: у слота, стоящего у соседа, этой модели в списке нет и быть не должно. Одно исключение
(1.34.0): слот у провайдера **без единого ключа** переезжает к провайдеру выбранного ключа той же
моделью (`ModelFamily`), когда доехал его каталог, — иначе человек только с ключом OpenRouter или
Anthropic получал бы «добавьте ключ Venice» на каждом слоте. По отказу каталога слот не переезжает
никогда: «Access Denied» по стране стёр бы выбор, который сработает, как только сеть пустит.

**Заводские модели — семействами.** Они записаны идентификаторами Venice (`AppSettings.Factory*`,
`DefaultFastModelId`), а у других провайдеров ту же модель находит `ModelFamily`: имя без
различий в написании (точка или тире в версии, дата снимка, приставка производителя) и известные
написания там, где имя своё (OpenRouter с производителем, DeepSeek напрямую — `deepseek-flash`).
`ModelSlotDefaults.Resolve` сначала ищет заводское семейство слота, потом запасной список
OpenRouter, потом приметы. Новый профиль получает «Авто» в чате (`CreateDefault`).
Исключения среди заводских семейств — модели OpenRouter: маршрутизатор и SynGuard — Jev 1.14
(модель Decisions), Роза — Aion 3.5 Mini (`FactoryFoxModelId`). Ревизия `FactoryModelsRevision`
один раз на профиль заменяет все модели и размышление, даже выбранные руками, включает SynGuard,
ставит поиск «Авто» и снимает привязки слотов к ключам; сами ключи остаются. Каждая новая замена —
следующий номер (`CurrentFactoryModels`): 2 — 1.35.0-beta.1, 3 — beta.2, и профиль, прошедший
прежнюю, проходит и новую. Файл без этого поля — ревизия 0: её ставит `IJsonOnDeserializing` до
чтения полей, а новый объект и `CreateDefault` — нынешняя. Второго разбора `settings.json` ради
этого не нужно: в beta.1 он шёл на каждом запуске.

У Aion 3.5 Mini размышление обязательное (`reasoning.mandatory` каталога OpenRouter →
`VeniceModelCapabilities.ReasoningMandatory`). «Без размышления» у OpenRouter — это отсутствие
поля `reasoning`, а без поля такая модель думает на своём уровне по умолчанию, у этой — high:
выключенное становилось самым дорогим. Поэтому `BuildOpenRouterPayload` шлёт такой модели нижний
уровень из каталога, а заводской уровень Розы — low (`FactoryFoxReasoning`).

**Сводка чата — слот, поиск в интернете — нет.** Слотов с 1.23.0 десять: добавился
`ModelSlot.Summary` (скрытая сводка переписки; прежде молча брала слот быстрого агента, и при
первом чтении старых настроек `AppSettingsStore.MigrateSummarySlot` переносит туда его модель
и ключ). А поиск — настройка **инструмента**: `AppSettings.WebSearchProvider` и
`WebSearchKeyId`, и модель человек не выбирает. Отдельной «ручки поиска» у провайдеров нет,
поиск едет надстройкой на обычном запросе (`venice_parameters` у Venice, плагин `web`
у OpenRouter), поэтому модель технически неизбежна — но подбирает её `ModelSlots.WebSearch`:
слот «лёгкие задачи», если он того же провайдера, иначе `ModelSlotDefaults`. Спрашивать о ней
человека значило бы спрашивать о том, что программа решает сама. **Пустой провайдер значит
«как у модели хода»** — так поиск работал до появления настройки. Закреплённый поиск платит
своим ключом: ради этого его и закрепляют. Третья настройка — движок OpenRouter
(`WebSearchEngine` + `WebSearchEngineMode`, готовые сочетания в `WebSearchEngines.All`): цена
у движков отличается десятикратно, поэтому она и показана в списке. Движок действует и при
пустом провайдере — если ход всё равно у OpenRouter; у Venice он не отправляется вовсе, лишнее
поле тот отвергает вместе со всем запросом.

**«Авто» меряет мышление ответа чата, а не работу на ПК.** Работу на машине делает агент со
своим маршрутизатором (`AgentTierRouter`), модель чата лишь ставит задачу и пересказывает отчёт.
Поэтому `ChatEngine.RouterSystemPrompt` не утяжеляет ответ из-за трудной работы агента — до
1.26.0 просьба «поставь драйвер и проверь Wi-Fi» уводила на флагман чата. Исключение одно
(1.32.0): сообщение о безопасности человека или этого компьютера (подозрение на угрозу, данные в
чужих руках, обман, защита от этого) идёт на heavy, даже когда работу делает агент, — ответ
должен оценить опасность и направлять агентов; уровень самого агента по-прежнему решает
`AgentTierRouter`. Правку этого промпта, как и промпта `AgentTierRouter`, проверяют прогоном на
живых запросах, а не вычиткой: `RouterLiveTests` (`AMARIN_ROUTER_LIVE=<файл>`, ключ из
`AMARIN_ROUTER_KEY` или `VENICE_API_KEY`/`OPENROUTER_API_KEY`, `%APPDATA%` не читает) гоняет
три десятка фраз через настоящий маршрутизатор и пишет таблицу.

**Отказ — вызовом `i_refuse`, и задачу берёт модель сильнее (1.36.0).** Отказ текстом программа
от ответа не отличала. Теперь отказаться можно только вызовом (`Refusals`: определение, разбор,
текст «Я, модель, отказываюсь…» — `S.Refusal.Final`); это не `ITool`, до шлюза он не доходит.
Чат (`ChatEngine.Refusal.cs`, проверка в `RunToolLoopAsync` сразу после потока, до записи в
историю) выбрасывает отказной ответ целиком и отдаёт ход ступени выше: лестница `[Heavy, Bypass]`,
место на ней — по самой модели (обход → выше некуда, тяжёлая → обход, любая другая, включая
выбранную руками, → обе), ступень с той же моделью пропускается. Модель, ключ и размышление
меняются на ходе (`VeniceTurnContext`), `messages` собираются заново под новую модель; выше никого
— ответ закрывается текстом отказа без висящего вызова. Агент на `i_refuse` заканчивает прогон
(вызовы ответа не исполняются, но каждый получает ответ — история остаётся парной), а решает чат:
`message_agent` или `agent_refused` (fast/lite → heavy → `bypass`, `AgentHost.NextTier`;
маршрутизатор уровней `bypass` не знает). Подъём убирает из истории **все** отказы агента, а не
последний (`AgentConversation.WithoutRefusals`), и `SynGuard.EarlierCalls` `i_refuse` не
показывает: с отказом, оставшимся после разговора с чатом, защитник читал «задача не выполняется»
среди сделанного и запрещал первый же шаг модели сильнее. Модель обхода — слот `ModelSlot.Bypass` (последний в
перечислении), заводская — Grok 4.7; ревизия заводских моделей ради него не поднималась.

**Агент отвечает чату до конца ответа (1.36.0).** Отчёт — реплика: «Отчёт агента a3: …», и чат
пишет агенту `message_agent` (`AgentHost.ContinueAsync`). Переписка агента — прежний механизм
`SessionMode.Continuous` (`AgentHost` ставит его всем прогонам; история сжата
`SessionHistoryCompressor`, у агента с мышью — через `Prepare`), а живёт она на ходе:
`VeniceTurnContext.Agents` → `AgentRunContext.Conversations`. Поэтому разговор кончается вместе с
ответом сам (так решил человек), расписание своего хода не имеет и разговора не держит. Id агента —
первая запись `AgentRegistry`; продолжения и пересадки записываются под тем же id (`Register(…, id)`),
чтобы «стоп» человека и сообщение чата говорили об одном агенте. Два вызова к одному агенту в
одном раунде — второй получает «занят» (`AgentConversation.TryEnter`). Продолжение плана не
показывает: записи идут через шлюз с вопросами. `message_agent` и `agent_refused` — чтения
(`ToolEffects`), своих переключателей не имеют: их выключает `init_agent` (`ToolCatalog.SwitchOf`).

**Выбранный ключ — это только про траты.** До 1.23.0 он задавал провайдера всем девяти слотам
сразу, и при смене выбор прятался в `ModelSlotStash`; тайника больше нет, поле
`AppSettings.ModelSlotsByProvider` оставлено лишь ради чтения старых файлов. Кружок на странице
«Ключи и траты» решает, чей остаток стоит на плашке и чьи траты показывает график, — поэтому менять
его посреди хода теперь можно (`MainWindow.OnSelectedKeyChanged`), а вот **добавлять, удалять
и возвращать** ключи по-прежнему нельзя: слот без назначенного ключа берёт его по провайдеру,
и исчезнувший ключ увёл бы следующий раунд в отказ. Переименование под запрет не попадает —
название не решает, чем платят. Ключ хода снимается при его начале и живёт на
`VeniceTurnContext.Credential` — вместе с моделью он съезжает и после маршрутизатора.

**Ключ уходит в другой профиль своим хранилищем.** «Отправить» в меню ключа (1.32.0,
`ApiKeyTransfer.Send`) открывает отдельный `ApiKeyStore` на папке того профиля
(`ProfileStore.DataRootFor`) и пароль не спрашивает: пароль профиля закрывает только окно, а
`keys.json` всех профилей зашифрован DPAPI одного пользователя Windows. `Add` делает новый ключ
активным, поэтому активный ключ того профиля после добавления возвращается на место. Ключ,
который там уже есть, не дублируется, а ключ окружения не отправляется вовсе: он и так виден
всем профилям. Уведомлений нет ни при отправке, ни при «уже есть» — так попросил человек.

**Чат уходит в другой профиль пакетом и сверкой (`Data/ChatTransfer`).** «Отправить | Переместить»
в меню чата (1.33.0) пишет копии одним `ChatStore` на папке того профиля и одной записью его описи,
в фоне (`MainWindow.TransferChatsAsync`), а потом сверяет **свежим** хранилищем: удаляется здесь
только то, что там видно в списке. Опись цели есть, но не читается — отказ без записи: иначе опись
из одного чата затёрла бы весь список того профиля. Чат с идущим ходом не переносится (пункты
приглушены): отмена хода до записи давала гонку — сохранение отменённого ответа возвращало чат и
сюда. С копией не едут выбор инструкций (библиотека чужая), машина, ключ и отметка расписания;
`UpdatedAt` — нынешний, чтобы чат встал наверх и не попал под правило хранения того профиля.
Черновик открытого чата уезжает с ним. Успех молчит, как у ключей; список профилей для обоих меню —
`ProfileRegistry.Others()`.

**Плашка выбора модели собирается один раз за кадр.** Хозяин за одно её открытие успевает
позвать `SetKeys`, `SetCatalog` и `SetSelected` по разу на каждого провайдера, поэтому
`ModelPickerPanel.Invalidate` не перестраивает столбцы сразу, а откладывает сборку на кадр
(`DispatcherPriority.Render`) и сливает вызовы в одну. Список моделей виртуализован
(`ItemsControl` + `VirtualizingStackPanel`, `ScrollUnit=Pixel`) и строится из
`ModelPickerRow`, а не собирается кнопками в коде: у OpenRouter моделей сотни, и
переиспользовать контейнеры панель умеет только для строк, нарисованных шаблоном по данным.
Поиск ждёт паузы в наборе, а пересборка пропускается, если провайдер, текст, фильтры и версия
каталога не изменились. Три правила, которые легко сломать обратно: `SetSelected` **не** трогает
показанный столбец провайдеров (иначе доехавший каталог возвращает его под рукой человека —
выглядит как «переключается через раз»); выбор ключа поднимает `KeyPicked`, а не `ModelPicked`
(хозяин закрывает плашку по второму); кнопки провайдеров заводятся по одной на провайдера и дальше
только обновляют состояние под `_suppressProviderEvent` — пересоздание поднимало `Checked` внутри
обработчика удаляемой соседки. С 1.34.0 столбец провайдеров прокручивается и упорядочен: с ключами
сверху, свои серверы — под своим названием; новый ключ своего сервера добавляет кнопку, удалённый
убирает её, а живые кнопки только переставляются. «Добавить ключ» у бледного провайдера несёт его
с событием — окно ключа открывается сразу на нём. В поле настроек (`ModelPickerField`) плашки нет, пока его не
откроют: девять собранных заранее плашек были половиной постройки страницы «Модели». Ключи,
каталоги и выбор поле помнит само и отдаёт плашке при создании, поэтому новое, что ей сообщают,
поле обязано запоминать тоже — иначе открытая позже плашка его не увидит.

**Пакетные модели OpenRouter идут через очередь, а не через `/chat/completions`.** У семидесяти
с лишним моделей есть вариант `…:batch` — та же модель вдвое дешевле, но обычный эндпоинт
отвечает ей 404 «This model is only available through the Batch API». Такой запрос ведёт
`VeniceClient.RunBatchAsync`: кладёт заявку в `POST /batches`, опрашивает `GET /batches/{id}`
до окончательного состояния и отдаёт обычный `ChatCompletionResponse` — снаружи это неотличимо
от синхронного ответа, поэтому агент, инструменты, учёт трат и запись переписки про очередь
ничего не знают. Правила очереди лежат в `OpenRouterBatchPlan` — отдельно от клиента, потому что
там нет ни сети, ни ключей, и они проверяются тестами напрямую. Что здесь легко сломать:

- **Порядок полей заявки — контракт.** Сервер разбирает тело потоком и отвечает 400, если
  `requests` встретился раньше `endpoint` и `model`; отсюда `JsonPropertyOrder` на каждом поле
  `OpenRouterBatchSubmit`.
- **В `model` заявки — слаг без пометки.** Пакетность задаёт сам эндпоинт, а `:batch` в каталоге
  лишь показывает половинную цену. Снимает пометку `ModelRef.WithoutBatchVariant`.
- **Очередь не берёт `stream`, плагин поиска и вложения строкой `data:`.** Первые два снимает
  `ToBatchBody`, вложения отбиваются до заявки (`UnsupportedReason`): отказ очереди приезжает
  минутами позже статусом `failed`, и человек всё это время ждёт ответа, которого не будет.
- **Служебная работа в очередь не ходит.** Заголовок, сводку, маршрутизатор, защиту и поиск в
  сети ждёт не человек, а сам ход, и сутки ожидания там — это просто зависший чат. Узнаётся она
  по пометке статьи расхода (`ChargeAs`) и по `AgentRunScope`, а не перечислением мест: их
  одиннадцать, и двенадцатое забыли бы. Такой запрос уходит обычным путём к близнецу без
  пометки — подменяет его `BuildOpenRouterPayload`.
- **Принятая заявка несколько секунд не существует.** Между `202` и первым успешным
  `GET /batches/{id}` очередь отвечает 404 «Batch job not found»: заявка сохранена, но ещё не
  видна. Это ход дела, а не отказ, и внутри окна проявления (`VisibilityWindow`, полторы минуты)
  опрос продолжается — иначе первый же опрос обрывает ход ошибкой, которую человеку не обойти.
  Окно отмеряется накопленными перерывами, а не часами: перерывы подменяются в тестах. Заявка,
  которая уже отвечала, а потом пропала, — это удалённая заявка, и её не ждут.
- **Отмена хода снимает и заявку.** Она уже стоит в очереди провайдера и будет посчитана;
  `CancelBatchQuietlyAsync` зовётся с `CancellationToken.None`, иначе общий токен отменил бы
  саму уборку.
- **Потока у очереди нет.** Пока заявка считается, на месте ответа идёт отчёт о её состоянии, и
  весь текст приходит разом в конце — иначе ход стоял бы немым минуты, а то и часы.
- Перерыв между опросами растёт до получаса (`NextDelay`), а в тестах подменяется через
  `VeniceClient.BatchDelay`: иначе каждая проверка ожидания стоила бы настоящие секунды.

Отказ провайдера, кстати, называет теперь того, кто отказал: зашитое «Venice API error» на ходе
через OpenRouter отправляло человека проверять не тот ключ.

**Каталог моделей — по одному на провайдера.** `VeniceModelListCache` держит запись на каждого
(`LoadAsync(provider)`, `CachedFor`, `ErrorFor`, `Invalidate(provider)`): плашка показывает оба
списка сразу. Провайдера без ключа не опрашиваем — запрос без `Authorization` вернулся бы
четырёхсоткой вместо понятного «добавьте ключ». **Запоминается только удача** (1.34.0): до этого
отказ ложился в кэш пустым списком, и человеку, которому OpenRouter ответил «Access Denied» по
стране, список не возвращался до перезапуска. Теперь `LoadAsync` не бросает (кроме отмены
вызывающим), отказ — строка `CatalogLoad.Error` из `ProviderErrorText.ForCatalog`, а следующая
просьба снова идёт в сеть: открытие плашки, нажатие на провайдера, открытие поля в настройках
(`ModelPickerField` поднимает `ProviderShown`) и кнопка «Повторить» под текстом отказа. Свой срок
загрузки — 30 с (у клиента пять минут, и плашка стояла бы на «Загрузка…»); одновременные просьбы
ждут одну загрузку. Окно `_appliedCatalogs` ставит только на удаче, а отказ раздаёт плашкам
(`SetCatalogError`), не трогая лечение слотов и поля размышления. Новая попытка уже загруженный
список не прячет. Тело отказа в тексте исключения — через `ProviderErrorText.Detail` (HTML-страница
сжимается до заголовка), а формат «{Провайдер} API error ({код}): …» и `VeniceApiException.StatusCode`
не трогаются: по ним `VeniceModelFallback.IsModelOverloaded` узнаёт 429/503.

**Модели Decisions (1.35.0)** доступны слотам «Маршрутизатор» и SynGuard. Каталог OpenRouter
загружается с `output_modalities=text,decisions`, без фильтра tools: обычный `/models` не
возвращает Decisions. `OpenRouterMapper` сохраняет выходную модальность в `Type`.
Общий кэш держит и разговорные модели, и Decisions с текстовым входом. `ForSlot` исключает
Decisions из остальных полей, команды выбора модели чата и подбора замен. Это правило нужно
применять и при поздней загрузке страницы настроек. Оба маршрутизатора используют
`CreateRoutingCompletionAsync`: обычная модель идёт через chat completions, Decisions — через
`/api/alpha/decisions` с вопросом choice. Расход записывается общим `RecordCost`; непонятный
выбор возвращает резервный уровень, но не теряет цену. Тип модели не записывается в настройки:
после импорта или запуска он читается из каталога, выбранный ID переносится обычным архивом.
SynGuard и обычный режим используют одну модель: вопросы `safe_to_run` и
`safe_without_approval` уходят одним запросом. Для `noul` true — значение выше 0.5. Вердикт —
по каждому вызову (`SynGuardReport.IsSafe`, `IsBlocked`, `IsUnchecked`): без вопроса запрещает
только **явное** «небезопасно» Decisions; ответа нет, он негоден, запрос упал или неизвестно даже,
Decisions ли модель, — вызов не выполняется сам, а идёт человеку с вопросом «SynGuard не
проверил» (`AlwaysAsk`), и только запись: чтение без вердикта идёт как шло. В beta.1 любой сбой
молча запрещал весь раунд, и у человека без ключа OpenRouter агент не мог записать ничего, пока
слот не переедет. Текстовая модель при сбое по-прежнему пропускает раунд. «Можно без вопроса»
снимает вопрос правил, «нужно подтверждение» ставит обязательный — кроме тихой записи
(`GateCheck.Quiet`: новый файл в «Загрузках», документ, созданный ИИ): её модель в вопрос не
превращает, так решил человек в 1.33.0. И вопрос, который правила задают всегда, модель не
снимает: отложенную команду и возврат программ (`Standing` — их выполнят без человека, а печать
ставится по этому согласию; его не минует даже «подтверждать всё автоматически») и неотмеченный
инструмент MCP (`ToolGate.ApplyNormalReview`); в beta.2 «можно без вопроса» снимало и их. При
выключенном SynGuard обычный режим всё равно задаёт модели вопрос о подтверждении. Жёсткие
запреты и режим чтения имеют приоритет. Журнал аудита узнаёт запрет SynGuard по
`GateDecision.GuardFlagged`, а не по тексту отказа; человеку запрет в ленте агента называет своя
строка (`S.AgentRun.GuardBlocked`), а не отказ для модели.
Оставлено как есть: пока каталог OpenRouter не загрузился, `UsesDecisionsAsync` качает его на
каждый вызов (только задержка, и только когда OpenRouter и так недоступен); текстовая модель в
обычном режиме — два запроса на раунд с записью, Decisions — один.
Для Decisions маршрутизаторы используют `RoutingDecisions`: короткий вопрос и отдельные
критерии исходов вместо текстового SystemPrompt. Примеры фраз и ситуаций в промпты не добавлять.
Сообщение о предполагаемой угрозе человеку, его данным или системе означает heavy, даже
без доказательств и подробностей. Угрозу оценивают и по описанным признакам и связи событий,
даже когда пользователь её не распознал. Неназванная тема сама по себе не означает угрозу.
Не смешивать это с прежними промптами текстовых маршрутизаторов. Поведенческую точность
проверять на живой модели;
тесты сериализации доказывают передачу правил, но не качество классификации.
`DecisionRouterLiveTests` запускается при `AMARIN_DECISION_ROUTER_LIVE=<файл отчёта>`
и `OPENROUTER_API_KEY`. По умолчанию использует Microsoft Decision 1, сохраняет настоящий
ответ, вероятности и ошибки API; сбой не считается классификацией lite. Примеры остаются
только проверочными входами и не попадают в инструкции или criteria.

**Журнал трат Venice отдаётся только админ-ключу.** Документация утверждает, что
`GET /billing/usage-history` открыт обычному ключу; на живом ключе он отвечает
`401 {"error":"Admin API key required"}`, а `GET /api_keys/rate_limits` рядом работает — поэтому
остаток показывается, а график пустовал. Основной источник графика — свой журнал
(`SpendLedger`), куда пишет `VeniceClient.AddCost`; журнал Venice берётся, только если ключ его
отдал. Отказ различается по `VeniceAdminKeyRequiredException` и не считается сетевым сбоем. Новое
место, где тратятся деньги, обязано звать `AddCost` с пометкой **и с теми учётными данными,
которыми заплатили**, иначе деньги попадут в журнал чужого ключа. У графика два режима —
«все ключи» и «один»: сводятся именно журналы (`SpendFold.Combine`), а не готовые отчёты,
потому что левый край периода «всё время» у каждого ключа свой. Ключи перед сведением
разбираются по `ApiKeyStore.Fingerprint`: ключ из окружения и его копия в `keys.json` — один
счёт.

**Цену ответа читают через `ChatCompletionResponse.ReportedCost()`.** Venice называет её полем
`cost`, OpenRouter — внутри `usage`. По этому правилу клиент списывает деньги в журнал трат
(`RecordCost`), и по нему же побочные запросы — маршрутизатор, заголовок, сводка, сжатие, поиск по
чатам, защитник, выбор уровня агента, отчёт — ставят свою строку в разбивку под сообщением. До
1.30.0 они читали только `cost`: у слотов на OpenRouter строки пропадали из разбивки, хотя на
графике деньги были, а маршрутизатор отдавал свои деньги строке модели. Новый побочный запрос
берёт цену так же, а не из `response.Cost`.

Прямые провайдеры цену не называют вовсе (`ProviderSpec.ReportsCost`): её оценивает сам клиент —
токены ответа × цена модели из каталога (`CostOf`) — и кладёт в `usage.cost` до возврата
ответа, так что правило выше работает и для них; оценка помечается `VeniceCost.Estimated`. Цены
моделей прямых провайдеров — из открытого каталога OpenRouter (`ModelPriceBook`): он же дополняет
их каталоги контекстом, зрением и уровнями размышления, которых те не называют. Книга лежит у
машины (`%LOCALAPPDATA%\AmarinAdminAI\prices.json`, раз в сутки) и спрашивается только ради
провайдера, которому нужна: у человека с ключом Venice программа в OpenRouter не ходит. Токены
едут вместе с деньгами (`VeniceCost.InputTokens/OutputTokens`) до `SpendLedger`, и запись без цены,
но с токенами, — тоже запись: у ключа с пакетом токенов это единственный учёт.

**Плашка остатка складывает все ключи.** Venice называет остаток на заголовках каждого ответа
(`x-venice-balance-*`), OpenRouter — только на прямой вопрос, и до 1.23.0 на его ключе плашка
стояла пустой навсегда. Теперь цифры каждого ключа лежат в `BalanceBook` (ключ — отпечаток
секрета, как и у файлов трат), заголовки наполняют её даром, а молчащие ключи дозапрашивает
`MainWindow.RefreshStaleBalancesAsync` — не чаще раза в пять минут на ключ, иначе у человека
с тремя ключами выходило бы три лишних запроса на каждое сообщение. На плашке сумма, под
курсором — разбивка и честное «ещё N — цифры пока нет». Между запусками книга лежит
в `balance.json`; файл прежнего формата (один остаток без владельца) читается как пустой.
Книгу и список ключей плашка берёт функциями: она собирается в конструкторе окна, а службы
привязываются позже — на этом порядке уже спотыкались.

**Разовый перенос трат — на профиль, а не на ключ.** Цены старых ответов лежат в самих
переписках, и `SpendLedger.Backfill` переносит их в журнал трат один раз. Отметка о переносе
стояла у ключа — и каждый заведённый позже ключ забирал себе всю историю чатов, оплаченную
предыдущим: два ключа показывали на графике одну сумму до цента. Какой ключ платил за
переписку, в ней не записано, поэтому отметка живёт в `AppSettings.SpendBackfilledAt`, а
`RepairDuplicateBackfills` разово вычитает уже случившиеся лишние импорты. Всё, что считает
деньги по ключу, обязано помнить: переписки принадлежат профилю, а не ключу.

**Предупреждение о лимите считается после записи цены.** До 1.32.0 его проверяли только перед
запросом: порог, перейдённый последним запросом, всплывал на следующем или никогда, а строка под
полем ввода снималась вместе с концом хода — видно её было, лишь пока шёл ответ. Теперь
`SpendSink` в корне композиции пишет цену в журнал и сразу зовёт `SpendGuard.AfterSpend`; ключ
«уже предупреждали» помнит сумму лимита и долю (поднятый лимит предупреждает заново), смена
профиля сбрасывает отметки (`ForgetWarnings`), а `NotifyStatus` кладёт строку под полем ввода на
12 секунд (`ShowStatusNote`), и её не снимают ни конец хода, ни смена чата. Проверка перед
запросом осталась: она задаёт вопрос «продолжить?» и ловит лимит, понижённый вручную.

**Аргументы инструментов от модели грязные.** Лишняя закрывающая скобка, два объекта подряд,
пояснение после закрывающей скобки, обёртка в ```` ```json ````. Разбирайте только через
`ToolArguments.Parse`, никогда не `JsonDocument.Parse` напрямую. Сборка вызовов из потока
(`ChatStreamAccumulator`) различает вызовы по `id`, а не только по `index`, — часть моделей
нумерует все вызовы нулём.

**В системных промптах — правило, а не разбор случая.** Задачи у людей самые разные, и расписанный
в промпте случай мешает решать все остальные: модель тянет ответ к нему и к похожим формулировкам
вместо того, о чём спросили на самом деле. Запрещён прежде всего разбор конкретного запроса —
приведённая фраза пользователя и расписанное к ней «отвечать надо так»; заодно «Например: …»,
образцы диалогов и перечни типовых задач. Остаётся правило, граница и формат: что модель делает
всегда, чего не делает никогда и в каком виде выдаёт ответ. Касается промптов роли `system`:
`Agent.BaseSystemPrompt` и `Agent.ExecutorRules` (агент), `ChatEngine.RouterSystemPrompt`
(маршрутизатор), `ChatEngine.DefaultTechPrompt`, `ChatEngine.TaskRules` и сборка
`BuildSystemPrompt` (чат), `BriefSystemPrompt`
(`ChatEngineInfographic`), `ChatTitle.SystemPrompt`, `LanguageTranslator.SystemPrompt` — и всякого
нового, который заведут рядом. Если без иллюстрации правило непонятно — плохо сформулировано само
правило; чините формулировку, а не добавляйте пример.

То же правило действует для описаний инструментов, их схем и текстов отказов: модель читает их как
указания. Пример там легко проглядеть, потому что он маскируется под образец синтаксиса. В 1.33.0
описание `edit_document` показывало `fill` формулой и диапазоном таблицы умножения, ровно того
случая, ради которого `fill` и завели. Поэтому формат показывают обозначением, а не значением:
A1-style, `YYYY-MM-DD`, `HH:mm`, «числа с единицами w, d, h, m, s». Из чата убраны и цитаты
русских фраз человека из промптов 1.14–1.16 (вида «найди / скинь картинку» или «диск D, а не C»):
вместо них стоит правило, которое они иллюстрировали. Промпт чата и описания его инструментов
сторожит `ChatPromptRuleTests`: там нет маркеров примера, кириллицы и значений на месте обозначений.
Новый инструмент чата попадает туда же, иначе тест упадёт на сверке с `ToolCatalog.Chat`.

**Инструкции пользователя видит только чат, и их оглавление — не техпромпт.** С 1.27.0 в папке
профиля лежит `instructions/<id>.md` (шапка `name/triggers/enabled/created` + Markdown; файл без
шапки тоже годится — название из имени файла). Хранит их `InstructionLibrary` — один объект на
программу, смену профиля он переживает через `UseRoot`, как `SpendLedger`. В системный промпт
чата идёт только оглавление (`InstructionBriefing.ForChat`: id, название, триггеры) — отдельным
блоком после `FormulaRules` и до блока моделей, **не** в `DefaultTechPrompt`, иначе до
сохранённых техпромптов оно бы не дошло. Текст модель берёт вызовом `read_instruction`.
Снимок инструкций хода берётся один раз (`ChatEngine.ActiveInstructions`), и по нему выбираются
и блок, и список инструментов: без включённых инструкций нет ни блока, ни инструмента. Путь к
файлу из аргумента модели не строится никогда — поиск только по загруженному списку. Кэш
перечитывает папку не чаще раза в две секунды и только изменившиеся файлы (время записи и
длина): кольцо контекста зовёт `CurrentSystemPrompt` на каждое обновление экрана. Агенту
инструкции не видны намеренно — чат передаёт нужное в постановке `init_agent`. Предел текста
(`TextLimit`, 10 000) держится ниже среза `ChatToolPreview.FormatForApi` — поднимете одно,
проверьте другое.

**Курсор, спрятанный на время набора, возвращает `CursorGuard`.** При включённом в Windows
«скрывать указатель при вводе» WPF прячет курсор первым же символом (`ShowCursor(false)`) и
показывает его только из `MouseMove`/`MouseLeave` **того же** поля. Поле, ушедшее из-под
неподвижной мыши (правка по Enter, сжатый композер), оставляло счётчик опущенным — курсора не
было над всей программой. Страж на каждое движение мыши зовёт WPF-овский
`TextEditorTyping._ShowCursor` (отражением: он сам сверяет свой флаг, счётчик не уезжает);
ставится в `Program` до первого окна. Своего `ShowCursor` в коде не заводите.

**Все инструменты — через один шлюз (`Security/ToolGate`).** До 1.28.0 инструменты чата не проходили
ничего: `write_file` из чата переписывал любой файл мимо режима подтверждений и SynGuard. Теперь и
`Agent.ExecuteToolCallsAsync`, и `ChatEngine.ExecuteRoundAsync` зовут шлюз, а своей логики защиты
не держат. Порядок: выключенный инструмент → классификация чтение/запись (`ToolEffects`;
**неизвестный инструмент или действие — запись**) → режим «Только чтение» → жёсткие запреты
(защищённые процессы и службы, чувствительные пути, запись в папку данных программы и снимков,
`LocalUsersSafety`) → SynGuard на раунд с записью → вопрос по режиму и разрешениям хода/чата →
снимок → исполнение → строка аудита. Шлюз никогда не бросает: любой исход — решение по вызову, и
пара «вызов — ответ» в истории модели не рвётся. Снимок решается отдельно от вопроса: вызов,
разрешённый SynGuard-вопросом или разрешением чата, снимок всё равно получает. Без шлюза
`ChatEngine` запись **отклоняет** — безопасное умолчание для тестов, где движок собирают руками.
«Новый файл в Загрузках/на Рабочем столе» проверяется самой записью (`SafeZone.CreateNewFlag` →
`FileMode.CreateNew`), а не заранее: два параллельных вызова иначе оба увидели бы «файла нет».
Новый инструмент, который пишет, — строка в таблице `ToolEffects`, а не обход.

**Путь файла шлюз видит таким же, каким его откроет инструмент.** Файловые инструменты раскрывают
относительный путь от «Загрузок» (и якоря `Desktop\…`, `Documents\…`), и до 1.33.0 шлюз смотрел на
сырой аргумент: `edit_file` по `settings.json` проходил запрет папки данных. Теперь `ToolGate.Check`
первым делом зовёт `FileToolPaths.CanonicalArguments` (поля `path` и `save_as`), и вопрос, аудит,
запреты и сам инструмент получают один абсолютный путь. Новый файловый инструмент — строка там же,
в `ProgramDataTarget` и, если создаёт новое без вопроса, в `ToolGate.Quiet`.

**Документ, созданный ИИ, разрешения не требует — ни на создание, ни на правку.** Так решил
человек (1.33.0). `ToolGate.Quiet` пропускает без вопроса две вещи: **новый** документ, картинку
или папку везде, кроме системы, папок программ, данных приложений (там же автозагрузка), чужих
профилей и сети (`DocumentZone`: канонический путь, без потоков `файл:имя`, без ссылок по пути), —
с условием «только новый файл», как и `SafeZone`; и **правку документа, который создал сам ИИ**
(`AiDocumentBook`, `ai-documents.json` в профиле, в архив не едет). Документ — только то, что не
запускается само (`DocumentZone.IsDocumentFile`): скрипт, конфиг или программа спрашиваются
всегда, где бы ни лежали. Файл узнаётся по пути **и времени создания**: человек, положивший на то
же место свой файл, получает вопрос, а сохранение в Word или Excel время создания не меняет.
Ставят отметку сами инструменты через `FileToolState.NoteWritten(…, aiDocument)`, а спрашивают
`IsAiDocument` **до** записи: подмена готовой копией может дать файлу новое время создания.
Шлюз смотрит в книгу через статический `ToolGate.AiDocument` (ставит `ApplyProcessWide`).
«Спрашивать всё» спрашивает и про документы ИИ, «Только чтение» не пускает запись вовсе.

**Правка — только прочитанного и не изменившегося (`Tools/FileToolState`).** Одна служба корня
композиции на все файловые инструменты и движок: что модель прочла в каждом чате (штамп «время
записи + длина») и замок по пути на весь цикл «прочитать — проверить — записать» — вызовы раунда
идут параллельно, и без замка две правки одного файла теряли одна другую. Правка на месте и
перезапись существующего требуют свежего чтения в этом чате; после успеха штамп обновляется, и
несколько правок подряд идут без перечитывания. Вложения отмечаются прочитанными при отправке.

**Вложение-документ уходит модели текстом, а файлом — только ручкой.** `DocumentDigest` разбирает
вложение в памяти (`DocumentSource` — поток, а не путь) и кладёт блок `<document name path>` с
началом текста и оглавлением; дочитывает модель `read_file` по ручке
`amarin-attachment:<sha12>/<имя>` (`ChatAttachmentRegistry`, по образцу `ChatImageRegistry`). До
1.33.0 вложения разворачивались копиями во `%TEMP%` открытым текстом — мимо `EncryptChats`, между
профилями и навсегда; копии старой папки удаляются при запуске. Разбор тяжёлый, поэтому прогрев —
на рабочем потоке (при добавлении вложения, восстановлении черновика, до `ForUser` в ходе и до
правки), а не на потоке окна. Правка по ручке на месте — отказ с советом `save_as`.

**Устаревшее уходит модели заглушкой (`Chat/ContextHygiene`).** В длинном чате о файле модель видит
его пять версий и цепляется за старую. `ContextHygiene.Apply` в `BuildApiMessages` правит только
копию для запроса: результат `read_file`, после которого файл меняли или перечитали то же место, —
«прочитай заново»; длинные аргументы старых вызовов — началом и пометкой; тела документов старых
сообщений — путём; прежние версии блока кода, если ниже есть две новее, — пометкой. Пары «вызов —
ответ» не рвутся, последние два хода человека не трогаются, хранимая история и отпечаток сжатия не
меняются ни на байт. Всё детерминировано — иначе кэш провайдера ломался бы на каждом запросе.

**Документы пишутся по схеме, а не «как получилось».** Word: порядок дочерних элементов по схеме
OpenXml, стили заголовков ищутся по имени `heading N` (в русском Word их Id другие). Excel: стиль
ячейки сохраняется при записи значения (клон `CellFormat` с нужным форматом числа), `CalculationChainPart`
выбрасывается при смене формул — иначе Excel предлагает «восстановить» файл, — лист переименовывается
вместе со ссылками. Подмена файла готовой копией повторяется несколько раз (`DocumentFiles.Replace`):
сразу после записи файл держат Defender и индексатор. PowerPoint — только чтение.

**Документы делает чат, сам и целиком, — и работу человеку не возвращает.** Человек хочет так
всегда. История ошибки поучительна: модель отдавала большой документ агенту («не помещается в один
вызов»); запрет агента на документы сделал хуже — модель стала писать человеку инструкцию «открой
Excel и сохрани PDF». Поэтому правила в `ChatEngine.FileRules` (доходит и до сохранённых
техпромптов) и в описании `init_agent` сформулированы через удобство человека: просили результат —
дай результат, а не шаги (шаги — только на «как сделать»); документы — своими инструментами,
агенту — только шаг, которого они не умеют, и звать его самому. **Правя этот промпт, проверяйте,
куда модель денется, когда «нельзя»: худший исход — работа, переложенная на человека.**

Объём и арифметику делает программа, а не модель. Excel: заполнение диапазона одной формулой или
рядом (`ExcelFill`: относительные ссылки сдвигаются, как при протяжке, `$` держит; текст в кавычках
и имена листов в апострофах не трогаются) — в `create_document` (`sheets[].fill`) и в
`edit_document` (`fill`). Итоги формул считает `ExcelCalc` (порядок операций Excel: `-2^2` = 4,
`2^3^2` = 64, `%` — постфикс; распространённые функции, ссылки на другие листы) и пишет в файл
`ExcelRecalc` после каждой записи книги; чего посчитать нельзя (динамические массивы, круг ссылок,
общая формула, формула массива) — не угадывается, остаётся Excel (`FullCalculationOnLoad`).
Документ из документа — `create_document` с `source` (`DocumentConvert`): Word, Excel со значениями,
PDF, PowerPoint, CSV и текст в Markdown, дальше обычная сборка; у Excel итог, которого нет в файле,
считается, а посчитать нельзя — отказ с тем, что делать. Секреты через `source` не читаются
(`SensitivePaths.IsSensitive`, как у `read_file`).

Большой документ строится частями в тот же файл: `edit_document` дописывает в конец Word и PDF
(`append`; у PDF это новые страницы — `PdfWriter.Render` и `PdfEditor.Append`) и строки в Excel
(`append_rows`). Таблица шире страницы печатается блоками столбцов с повтором первого
(`MarkdownBlocks.ColumnBlocks`; в PDF у столбца есть наименьшая ширина `PdfLayout.MinColumn`, и
до этого всё правее четырнадцатого столбца молча уходило за край, а в Word между блоками нужен
абзац — две таблицы подряд он склеивает).

**PowerShell разбирается деревом, а исполняется в 5.1.** `PowerShellAnalysis` строит AST парсером
`System.Management.Automation` 7.6, но скрипты запускает `powershell.exe` 5.1 — поэтому словарь
псевдонимов по 5.1 (`sc` — это `Set-Content`, `curl` — `Invoke-WebRequest`). Чтением считается
только разрешённое списком (глаголы Get/Test/…, безопасные методы, внешние программы с
подкомандами чтения); всё остальное, пустое и неразобранное — запись (fail-closed). Причины идут
в окно подтверждения, и каждая урезана до 48 знаков: длинная раздувала сводку так, что код
скрипта уезжал из окна. Загрузка мимо белого списка и смена учётки не константой — отказ с советом
взять `download_file`/`local_users`.

**Отложенные задачи ничего не теряют молча (`Amarin.Core/Deferred`).** Чат ставит их инструментом
`deferred_task` (напоминание, задача агенту, команда, возврат программ прошлого сеанса; срок,
промежуток, время работы Windows, следующее включение, следующий запуск, условие; повтор). Правила,
на которых держится «не теряется»:
- **«Выполняется» пишется на диск до запуска** (`DeferredRunner.FireAsync`); при следующем запуске
  такая задача становится «прервалась», и человек решает, повторять ли — запись в систему без
  человека дважды не повторяется. Неподтверждённое напоминание при запуске встаёт снова.
- **Пропущенное срабатывает один раз** с пометкой «опоздало на …», без очереди за все пропуски.
  «Каждый день в 9:00» считается по местным часам при каждой перестановке и на `TimeChanged`.
- **«Следующее включение» — вход в Windows, а не загрузка** (`SystemSession`: время входа WTS):
  быстрый запуск Windows загрузку не сбрасывает. Аптайм — `Environment.TickCount64`, как в
  Диспетчере задач, ради чего напоминание о перезагрузке и нужно.
- **Занятый чат — «позже», а не попытка**: прогон возвращает null, задача ждёт полминуты. Три
  неудачи подряд останавливают повтор (`Paused`), а не жгут деньги.
- **Команда одобряется при постановке**, и `ConfirmationQueue` для таких вопросов (`Standing`) не
  даёт ни «подтверждать всё», ни «разрешить на чат»: одно «да» одобрило бы будущие скрипты без
  человека. Команда и возврат программ несут печать HMAC (`DeferredBook.Seal`, ключ под DPAPI в
  `deferred.key`) — из чужого архива или после правки руками не выполнятся. Исполнение идёт тем же
  `GateRun`, что у рецептов: жёсткие запреты и «только чтение» действуют. Условие только читает.
- `deferred.json`, `deferred.key` и `last-session.json` в архив данных не едут.

Агент и команда исполняются ходом `TurnKind.Deferred` в чате задачи (`MainWindow.Deferred.cs`):
живой объект хода или открытого чата раньше файла, удалённый чат — новый. Агент — без плана (план
ждал бы человека вечно, `AgentRunContext.PlanAllowed`), с потолком цены и сроком 2 ч. После первого
агента ход идёт обычным циклом с инструментами (`RunAgentCommandAsync(continueWithTools: true)`), а
не одним отчётом без них, как у `/agent`: отчёт без инструментов писал «запускаю агента ещё раз» и
не мог позвать его — человека рядом нет, и задача оставалась несделанной. Карточки
напоминаний — своя стопка (`ReminderToast` + `ReminderStack`), а не `Notify`; итог прогона — через
`Notify`. Мелодия — `ChimeSynth` (синтез, без файлов), молчит в «тихие часы» (`QuietState`).
Закрытую программу будит задача Планировщика (`SchtasksDeferredWake`, `--wake`): XML собирает
`DeferredWakeTask`, и каждое значение там — против вредного умолчания (72 часа на работу, низкий
приоритет, запрет от батареи); `schtasks` зовётся, только когда нужное отличается от
поставленного, что поставлено — помнит отметка в `%LOCALAPPDATA%`. Окно в тестах сроки само не
проверяет (`StartDeferred(inTests: true)` — явно), а стопка в тестах окно не показывает
(`ShowWindow`): иначе заготовленная задача выставила бы карточку в угол настоящего экрана. Модели
дата хода — последней строкой промпта (`ChatEngine.DateLine`, раз в сутки), точное «сейчас» —
в ответе инструмента.

**Варианты ответа — «тайник» на якоре.** Активная ветка всегда лежит в плоских `Messages` и
`ApiMessages`: сборка истории, отрисовка, сводка и дозапись работают как раньше, старые файлы
читаются без миграции. Спрятанные ветки — `ChatBranch` в `Variants` у якоря (ответ при
«Повторить», вопрос при правке), вложенные живут внутри спрятанных. Группу держит только активный
якорь: правка якоря с вариантами сначала **переносит** группу на новый якорь — иначе список
вложился бы сам в себя. Все операции — `ChatBranches` под `session.Gate`, его же берёт сериализация
в `ChatStore`. Развилка делается внутри хода (`RunTurnAsync`), когда он уже зарегистрирован: между
«спрятали» и «появился якорь» нет окна, где сохранение потеряло бы и старый ответ, и новый.
Переключение запрещено, пока чат отвечает. Кто считает деньги, картинки или журнал, обходит
`ChatBranches.All`; поздние записи (цена сводки) ищут сообщение через `FindMessage` во всех
ветках. «Поделиться» и экспорт чата несут только активную ветку, архив данных — всё.

**Служебные строки раунда — маркеры на диске (`Chat/EngineLines`).** `ToolRound.InfoLine` и
`ResultPreview` («Запускаю инструменты», «Инструменты завершены - запрашиваю ответ модели (шаг N)…»,
«отменено») лежат в файлах чатов и **сравниваются** — адаптер агента узнаёт по ним раунд, лента —
строку, которую не надо дублировать. Поэтому они пишутся русскими константами, а переводится
только показ (`EngineLines.Display`), как у `ChatTitle.Default`. Сравнивать их с переводом нельзя:
до 1.28.0 лента сравнивала с `Loc.Get(...)`, и в английском интерфейсе русский маркер
показывался как есть.

**Шифрование на диске — байтами и под замком файла.** При `AppSettings.EncryptChats` чаты,
`chats/index.json` и новые строки журнала аудита пишутся под DPAPI (`AtRestCipher`, метка
`AMRN-DPAPI1` в начале файла, у строки — `!amrn-dpapi1:`); читаются оба формата всегда. Смена
галочки переписывает файлы в фоне (`ChatStore.EnsureFormat`) **байтами**, под тем же замком
файла, что и обычная запись очереди: разбор в `ChatSession` и повторное сохранение затёрли бы
свежий ответ идущего хода копией с диска. Цель запоминается при вызове — после смены профиля
`Encrypt` смотрит на чужие настройки, поэтому `UseProfile` зовёт `StopReformat`. Отпечаток
записанного включает формат, иначе нетронутый чат так и остался бы открытым. Архив данных
расшифровывает (DPAPI на другой машине бесполезен), импорт пишет по настройке того профиля,
куда кладёт. `EncryptChats` и `AutoLockMinutes`, как и режим доступа, из чужого архива не
приезжают. В тестах «секрет» пишите латиницей: JSON кодирует кириллицу как `\u043F…`, и русская
строка не нашлась бы и в открытом файле — проверка «шифр прячет текст» прошла бы и без шифра.

**«Удалить все данные» стирает преемник.** Пока окно живо, файлы пишутся отовсюду (закрытие
сохраняет размер окна, запоздавшие сводка и заголовок — свой чат), и стёртое на ходу вернулось бы.
Поэтому окно оставляет `wipe-request.json` в корне данных (`PendingWipe.Request`), запускает себя
с `--await-exit <pid> --wipe <метка>` и выходит; преемник стирает **до того, как прочтёт хоть один
файл** (`PendingWipe.Run` в начале `RunWpf`). Ключ без файла с той же меткой ничего не стирает —
иначе ярлык с `--wipe` уничтожал бы данные без вопроса; просьба старше пяти минут тоже. Выход ради
стирания не доводит обновление (`_wipeRestart`): преемник ждёт прежний процесс лишь полминуты. У
профиля по умолчанию стирается только перечисленное в `ProfileDataWiper` — корень общий, там же
`profiles.json`, чужие профили и переводы.

**Экран блокировки прячет слои под собой.** `LockScreen` — последний слой `ScaledRoot`; на время
блокировки остальные слои получают `Opacity = 0` и `IsEnabled = false`. Одной подложки мало:
заливка окна в оформлении «стекло» полупрозрачна, а вопрос об опасном действии, пришедший под
блокировкой, лёг бы поверх неё; неактивные слои ещё и не берут фокус. Клавиатура под блокировкой —
только полю пароля (`KeepKeyboardOnLock` первым делом в `Window_PreviewKeyDown`/`PreviewTextInput`),
уведомление о готовом ответе текста не показывает. Пароль проверяется на рабочем потоке — PBKDF2
заметно держал бы интерфейс.

**`UserControl` со `StaticResource` на общие стили подключает `Resources.xaml` сам.** Словарь
подключён ресурсами главного окна, не приложения, а `StaticResource` разбирается при создании
контрола, когда тот ещё не вставлен в окно. `LockScreen` без своего подключения не находил
`LockChromeButton`, окно не собиралось, и на Windows падали все оконные тесты — на Linux XAML
такого не разбирает, там это не видно.

**Поле пароля само принимает набранное.** `ShouldKeepKeyboardFocus` уступает ввод элементам из
`TakesTypedText` — редактируемым `TextBox`/`RichTextBox` и `PasswordBox`. До 1.28.0 `PasswordBox`
там не было, и пароль, набранный в поле архива, окно переложило бы в поле сообщения — то есть в
чат с моделью.

**Рамка фокуса — только у элементов-действий.** `AccessibilityDefaults.ApplyFocusFrame` ставит
рамку цветом акцента элементу без своей, только если это `ButtonBase` (кнопки, переключатели,
галочки, радио), `ComboBox` или `Slider`; всем остальным — `FocusVisualStyle = null`, иначе
вылез бы системный пунктир. Полям с текстом рамки нет с 1.32.0: фокус в поле видно по каретке,
а рамка обводила поле ввода всякий раз, когда фокус приходил туда с клавиатуры (окно само
переносит в поле набранное в колонке чатов или ленте, `FocusMessageInput`), и тексты ответов
(поля только для чтения) обводились бы целиком. Контейнерам — прокрутке, списку целиком, слою
поверх окна — рамки нет с 1.36.0: фокус в них ставит сам код ради клавиш (колонка чатов,
навигация настроек, «Состояние ПК»), и после любой клавиши акцентом обводилась вся колонка или
слой — человек видел рамку на «случайном» крупном элементе. Новый вид элемента-действия, которому
рамка нужна, — строка в той же проверке.

**Обновление ставится только сверенным.** Сумма SHA-256 берётся из `digest` ассета, а нет его — из
`SHA256SUMS` того же релиза; без суммы автозагрузка и выход с подменой ничего не ставят, а кнопка
предлагает «Обновить без проверки» с отдельным вопросом. `UpdateInstaller.VerifyBeforeSwap`
сверяет файл ещё раз прямо перед подменой — и в `Swap`, и в `ApplyElevated` (повышенному процессу
сумма уходит ключом `--sha256`): файл во временной папке доступен пользователю, и без повторной
сверки подмена от администратора была бы дырой. Подпись — правило `AuthenticodeCheck.Refusal`:
подписанную программу меняет только файл того же издателя с целой подписью, неподписанную —
решает сумма.

**Новую версию находят и без API GitHub.** Анонимный API отвечает шестидесяти запросам в час
**на адрес**, и за VPN, мобильным NAT или общим офисным выходом лимит выбирают чужие запросы. До
1.28.5 запасной путь (`/releases/latest` → редирект на тег) давал версию без файлов: кнопки
«Обновить» не было, автообновление не качало ничего, а повторная проверка затирала уже найденный
полный выпуск бедным — кнопка пропадала посреди сеанса. Теперь `UpdateChecker` уходит на запасной
путь при **любом** отказе API (статус, обрыв, `ApiTimeout` в 10 секунд из 30 общих), а сборку и
сумму берёт из `SHA256SUMS` по прямой ссылке `releases/download/<тег>/…` (`ReadBuildFromSums`) —
поэтому `release.yml` обязан выкладывать этот файл всегда, а имя exe в нём — то, под которым он
выложен. Тот же выпуск, найденный беднее, известного не затирает (`UpdateChecker.Richer`). Номер
новой версии есть в каждом состоянии и в метке боковой колонки.

**Обновления — конечный автомат, а не поля окна (`Amarin.Core/Updates`).** С 1.30.0 все решения
принимает чистый `UpdateMachine.Next(состояние, событие, контекст) → (состояние, эффекты)`; сеть,
диск и процессы исполняет `UpdateController` через порты (`IUpdateSource`, `IUpdateFiles`,
`IUpdateApp`), а выход с обновлением — `UpdateExit` (`IExitHost`). Плашку рисует одна функция
`UpdateView.From(состояние)`; окно только переносит её на контролы (`RenderUpdates`) и подаёт
нажатия. Новое правило — ветка в редьюсере и тест в `UpdateMachineTests`, а не поле в окне.
Что здесь легко сломать:

- **«Обновить» во время фоновой загрузки присоединяется к ней**, а не отменяет (до 1.30.0 кнопка
  была подписана «Отмена» и обрывала загрузку). «Отмена» — только у загрузки, которую уже ждёт
  человек (`UpdateDownload.Wanted`): по кнопке или присоединённой.
- **Итоги сетевых шагов несут номер** (`CheckGeneration`, `DownloadGeneration`): опоздавший
  ответ проверки прежнего канала и отчёт отменённой загрузки отбрасываются по чужому номеру.
- **Скачанная v1 и качающаяся v2 живут рядом** (`Staged` и `Download`): выход ждёт v2 до
  `ExitLimit` и только потом ставит v1.
- **Неудача — факт в состоянии** (`Failure`, `RestartError`), а не строка на плашке: следующая
  перерисовка не должна возвращать «Есть обновление» поверх «Не удалось». Разовые строки
  (`UpdateNotice`) снимает открытие страницы, только если это ответы на нажатие (`Transient`).
- **`SwapDone` закрывает всё**: после подмены нет ни проверок, ни загрузок, ни второй установки
  при выходе — даже если перезапуск не удался.
- Драйвер живёт на потоке окна без замка; событие, поданное изнутри эффекта, встаёт в очередь
  (`Dispatch`). Выход ждёт **состояние** (`WaitUntilAsync`), а не задачу: итог задачи ещё должен
  дойти очередью до автомата.
- В тестах подделки завершают сетевой шаг вне контекста ручной очереди
  (`UpdateTestKit.OffUiThread`): продолжение `await … ConfigureAwait(false)` не встраивается туда,
  где стоит свой `SynchronizationContext`, и итог приходил бы в очередь когда придётся.
- **Отмена откладывает версию до следующего запуска** (`UpdateState.Postponed`, только в памяти):
  следующая проверка её не качает, выход не докачивает и не ставит. Правило одно —
  `UpdateMachine.WantedAutomatically(state, release, context)`, его зовут и автомат, и
  `UpdateExit.PendingForExit`; новое место, которое решает «качать ли само», берёт его же.
  «Обновить» и смена канала отметку снимают. До 1.30.0 отмена не держалась вовсе.
- **Значок в шапке и его попап рисует тот же `RenderUpdates`** по `UpdateView.Badge` и
  `CanCancelDownload`: одно состояние, три места (значок, попап, карточка в настройках), и
  разойтись им нечем. Неудачная проверка значка не зажигает — о ней говорит карточка. Окну
  подставляют подделки шовом `UseUpdatePorts` — так оконные тесты проходят кнопки целиком без сети.
- **Загрузка идёт попытками с докачкой (`ResumableDownload`, 1.32.0).** Медленное или повисшее
  первое соединение раньше нечем было заменить, и автозагрузка на запуске тянулась бесконечно,
  а «Отмена» → «Обновить» помогала только тем, что открывала новое. Теперь сторож внутри загрузки
  меряет байты, а не проценты (`DownloadPolicy`: 20 с тишины или меньше ~128 КБ/с за 10 с),
  обрывает попытку и просит `Range` с полученного байта на новом соединении HTTP/1.1; ответ 200
  или чужой `Content-Range` начинают файл заново, после четырёх перезапусков качается как есть.
  Отмена — только токен человека: таймаут клиента — это зависание с отказом `S.Updates.Stalled`,
  а не молчаливая отмена. Своего сторожа у `UpdateController` больше нет. Часы — `TimeProvider`;
  в тестах `ManualTime` двигают по секунде, иначе таймер сторожа срабатывает один раз за весь шаг.

**Журнал аудита только дописывается.** `audit/yyyy-MM.jsonl` в папке профиля, строка — одно
открытие на дозапись. Пишется каждая запись в систему и каждый отказ (`AuditLog.Worth`), удачное
чтение — нет. Секреты вычищаются по имени поля и списку `CrashHandler.Secrets`. Удаление чатов
журнал не трогает — ради этого он и отдельный; импорт только дописывает, повторы отсекаются по
`id`. `--smoke-tools` зовёт инструменты мимо шлюза и в журнал не пишет.

**Сообщить или переспросить — `ShowNoticeAsync`, не `MessageBox`.** Системное окно рисовалось
чужим стилем и в системном масштабе (`UiScale` подменяет DPI только нашему окну). Уведомление —
слой `NoticeOverlay` с необязательным своим содержимым (галочка, поле для слова); новый вопрос
поверх незакрытого снимает прежний ответом «нет».

**Настройки — 720×520, одиннадцать страниц, вид концепта.** Вид задан картинками концепта
(`amarin-concept/after`), а не словами: прошлый передизайн, сделанный по описанию, вышел плоскими
списками и был отвергнут. Навигация — три подписи групп (Основное: Общие, Оформление, Профиль;

**Настройки строятся после первого кадра.** Конструктор окна их не создаёт: оболочку и по
странице за порцию собирает прогрев в простое (`MainWindow.SettingsHost.cs`,
`ScheduleSettingsPrewarm`, `DispatcherPriority.ApplicationIdle`), первыми — «Общие». Открытие
раньше прогрева (`OpenSettings` — единый вход для шестерёнки, Ctrl+, и ссылок на страницу)
достраивает оболочку и одну страницу. Обработчики остались в тематических partial-файлах окна, а
подписывает их `OnSettingsPageCreated`, когда страница создана: атрибуты событий в разметке
UserControl искали бы методы у самой страницы. Отсюда три правила:
- к контролу окно обращается через страницу (`GeneralPage.AutoScrollToggle`), и свойство страницы
  создаёт её при первом обращении. Код, который пишет в страницу из фона, при запуске или смене
  языка (`RenderUpdates`, `RefreshBehaviorLinks`, `BackupPanel.ShowStatus`, …), берёт её через
  `BuiltPage<T>()` и страницы не создаёт: созданная позже, она заполнится из настроек сама;
- значения ставит `LoadSettingsPage` под `_settingsUiLoading`, один раз при создании и заново при
  показе, если настройки с тех пор перечитали (открытие, смена профиля, импорт — `LoadSettingsUi`
  помечает построенные страницы устаревшими и применяет к окну тему, оформление, углы, масштаб);
- тяжёлое содержимое подстраниц (53 карточки тем, 13 строк сочетаний) строится своей порцией
  прогрева или при первом заходе на подстраницу (`_settingsDeferred`, `SettingsDrill.Opened`);
  плашку выбора модели `ModelPickerField` создаёт при первом открытии, образцы цвета
  `ColorPickerField` — тоже. Порция прогрева — одна страница или одно такое содержимое.
Страница, созданная в свёрнутом слое, не получает `Loaded`, пока её не покажут, — тест, которому
нужен загруженный шаблон (плавный скролл поля), сперва показывает страницу. Тесты ищут контролы
через `SettingsTestKit.FindSetting` (строит всё, как закончившийся прогрев) вместо
`window.FindName`; ленивость сторожит `SettingsLazyTests`.

**Всплывающие окна — из одного набора стилей.** `Resources.xaml`: `DialogCard`, `DialogTitle`,
`DialogText`, `DialogLabel`, `DialogField` + `DialogInput` (подсказка в пустом поле — из `Tag`),
`DialogSegment` для выбора из двух-трёх, `DialogFooter`, кнопки `DialogPrimaryButton`,
`DialogSecondaryButton` и `DialogDangerButton` (красная подпись у необратимого). Заголовок — вопрос
или действие («Удалить чат?», «Разрешить действие?»), под ним одна строка, только если без неё не
понять; абзацев пояснений и цветных точек у заголовка нет. Ошибка и «Проверяю…» пишутся в подвал
слева от кнопок: окно стоит по центру, и строка ошибки под полем меняла бы его высоту — окно

сообщить — `Inform`, спросить — `ShowNoticeAsync`.

**Состояние не двигает раскладку.** Выбранный пункт полужирный — значит, рядом с подписью лежит её
полужирная копия-невидимка (`Visibility="Hidden"`), которая держит ширину: иначе соседние вкладки
сдвигались на пару точек при каждом переключении. Папка в боковой панели — всегда карточка
(`ChatRowState.Band`): у свёрнутой и раскрытой одинаковый верх, и раскрытие только растит её вниз.
Шапки вкладок Automation одной высоты и в одну строку. Заголовки всех страниц настроек стоят в
одной точке (`SettingsRedesignTests`).

**Снимки интерфейса — тестом `UiShotTests`.** С `AMARIN_UI_SHOTS=<папка>` (и, если надо,
`AMARIN_UI_SHOTS_ONLY=NavGeneral,health,dialogs,updates,icons`) он рисует в PNG каждую страницу и
подстраницу настроек, редакторы, боковую панель, «Состояние ПК», всплывающие окна, обновления
(значок в шапке, попап и карточку в восьми состояниях) и лист значков навигации — по-английски и
по-русски, в тёмной и светлой теме, с открытым разговором в ленте. С фильтром снимается один
вариант; `AMARIN_UI_SHOTS_ALL=1` — все четыре; `AMARIN_UI_SHOTS_THEMES=Contrast,…` (или `all`) —
русский интерфейс в перечисленных палитрах; `AMARIN_UI_SHOTS_MIN=1` добавляет маленькое окно. Без
переменной тест сразу выходит. Длинные страницы режутся на куски по 900 точек. Съёмка, которая
подставляет состояние (обновления), идёт последней и возвращает прежнее: открытые раньше времени
настройки включают кнопку микрофона, и она попадала на снимки диалогов.

**Замеры скорости — тестом `PerfBenchTests`** (`AMARIN_PERF_BENCH=<файл>`, сборка Release,
отдельный процесс): запуск окна, открытие чата на 1200 сообщений, перетаскивание края,
разворот, оверлеи, раскрытие папок. Рядом со временем по часам пишется время процессора потока
окна: при погашенном мониторе DWM составляет кадр раз в секунду, и WPF на каждом изменении размера
ждёт показа — пустое окно тянулось по 200 мс на шаг. Первая строка таблицы — сколько раз в секунду
обновлялся экран. Шаг `GetThreadTimes` — 15,6 мс; ЦП всего процесса в первые секунды после
открытия окна — фоновая компиляция JIT, а не работа программы.

**Тень попапа — `PopupShadow`.** У попапа своё прозрачное окно ровно по содержимому, и тень за
краем карточки видна только в её полях. Тень и поля одни на всех (`PopupShadow.Effect` 24/6/0,5,
`PopupShadow.Margin` 16,16,24,24: тень доходит до 14 и 22 точек, ещё две — запас на округление
при масштабе), через `x:Static`: их видит и `UserControl` без своего `Resources.xaml`. Смещение
попапа возвращает поля так, что карточка стоит, где стояла (у меню — сеттеры
`HorizontalOffset`/`VerticalOffset` в `AppContextMenu`). Новый прозрачный попап с тенью берёт их
же — это сторожит `PopupShadowTests`, вместе с полной прозрачностью края окна попапа и местом
карточки. Меняя поля, сдвигайте смещения всех попапов на ту же величину.

**Общий поток интерфейса в тестах не умирает молча.** `WpfUi` пишет необработанные исключения
общего потока в `wpf-ui-thread-errors.log` рядом со сборкой тестов и оставляет поток живым;
прогон `Tests` печатает этот журнал. Выход через `RequestExit` — дело только главного окна
приложения (`OwnsApplication`): тестовое окно рядом с общим закрывается само по себе, а не гасит
`Application` посреди чужого теста.

**`using System.IO` подключён неявно, а WPF-пространства — нет.** В csproj `System.Windows`,
`System.Windows.Controls`, `System.Windows.Media` и прочие явно удалены из неявных using, поэтому
в каждом файле их пишут руками. Обратная сторона: `System.Windows.Shapes.Path` конфликтует с
`System.IO.Path` — нужен псевдоним `using Path = System.Windows.Shapes.Path;`.

**Блок кода сам решает, куда листать ленту.** Блок — свой `RichTextBox` внутри
`BlockUIContainer` документа ответа, и прокрутка этого документа (FlowDocumentView) переводит
прямоугольник вложенного элемента в верх сообщения. До 1.32.0 щелчок по коду ставил каретку,
редактор просил показать её, и лента уезжала к началу ответа прямо под мышью, а выделение
тянулось вверх по всему блоку; щелчок правее строк ловил редактор самого ответа и уводил ленту к
концу блока. Теперь корень блока гасит `RequestBringIntoView` и поднимает его заново с родителя
документа, в его координатах (`CodeBlockView.ForwardBringIntoView`): выделение за край ленты
по-прежнему листает её за кареткой, а просьбу показать блок целиком (её шлёт фокус) после мыши
блок не передаёт. Левое нажатие на свободном месте блока гасится там же. Новый элемент со своим
редактором внутри документа ответа требует того же приёма. Найдено настоящей мышью: синтетическое
нажатие редактор не разбирает — он берёт место настоящего курсора, — поэтому `CodeBlockScrollTests`
поднимает те же просьбы показать, что и редактор, а путь нажатия проверяет по документу ответа.

**Правила подсветки ColorCode исправлены на месте (1.36.0).** Подсветка идёт на потоке окна при
каждой перерисовке потока, а в дописываемом блоке строка и комментарий почти всегда незакрыты. У
ColorCode 2.0.15 часть правил с вложенным повтором (строка JSON, `/* */`, `<!-- -->`, атрибуты
тегов, строки F# и Koka, `{- -}`, вложенный блок markdown) на неудачном разборе перебирает варианты
экспоненциально — программа висела навсегда посреди ответа с JSON. `CodeHighlighterFixes`
(статический конструктор `CodeHighlighter`, до первой компиляции языка) подменяет такие куски на
тот же язык без перебора и регистрирует язык под тем же `Id` — его же возьмёт вложенная подсветка.
`CodeHighlighterSafetyTests` прогоняет каждое правило каждого языка на незакрытых конструкциях с
пределом времени и сверяет, что замены читают обычный код так же; обновили ColorCode — сперва этот тест.

**Разметка чата.** `MathBlock` из Markdig наследуется от `FencedCodeBlock`, поэтому его `case`
обязан стоять раньше — иначе формула уедет в блок кода. Формулы приводятся к долларам до разбора
(`MathDelimiterNormalizer`), а содержимое одиночных `$…$` проходит проверку `MathDetection`:
без неё `$env:VENICE_API_KEY` в ответе про PowerShell превращался в формулу. Тем же проходом
`MathAutoWrap` заворачивает в доллары формулы, оставленные моделью без них (голый LaTeX и
математика обычным текстом); строки с `$`, код и середина `$$`-блока не трогаются, и каждое новое
правило там обязано идти с тестами на то, что пути, даты и команды остались текстом. Слэш между
простыми операндами `LatexParser` набирает дробью (кроме индексов и степеней). `MathDetection`
принимает и выражения без знаков операций — `|z|`, `f(x)`, `(x, y)`, — но только из одиночных
букв и имён функций: слово длиннее — проза или переменная оболочки. В рендере мнимая единица i
прямая, если формула не берёт i индексом (`MathRenderer.UsesIAsIndex`), а перед именем функции
стоит тонкий промежуток — курсивная i в Cambria Math иначе терялась в «isin». Формула в строке
садится на базовую линию через `TextBlock.BaselineOffset` (его читает `InlineObjectRun.Format`),
а **не** отрицательным нижним отступом: с отступом строка не оставляла места под свес, и
следующая строка печаталась поверх знаменателей. Абзац с формулой — где угодно, хоть внутри
`**…**` — отпускает интерлиньяж (`RelaxLineHeight`). Курсивная буква несёт поправку на наклон
(`MathVisual.ItalicCorrection`): у Cambria Math нет своего курсива, WPF наклоняет прямую букву
за её ширину. Чату правило
о формулах дописывается блоком `ChatEngine.FormulaRules` в `BuildSystemPrompt` — не в
`DefaultTechPrompt`, иначе до сохранённых техпромптов оно бы не дошло.

**Копии настроек клиента — только через `with`.** Проверку до платного запроса делает
`SpendGuard` через `AgentOptions.SpendGate`, а копий `AgentOptions` много — агент
(`AgentHost.CloneOptions`), сводка, заголовок, отчёт. До 1.30.0 их собирали `new AgentOptions { … }`
с перечислением полей, и все четыре теряли `BalanceSink` — остаток из их ответов до плашки не
доходил; так же забытый делегат лимитов пропустил бы запросы мимо них молча. С 1.30.0
`AgentOptions` — запись, копия — `source with { … }` и наследует каждое поле (`AgentOptionsCopyTests`);
`ToString` у записи переопределён, чтобы не печатать ключ. Потолок хода считается по `SpendScope`: он, в
отличие от `VeniceTurnScope`, переживает `Suppress` у агентов, иначе агент тратил бы без счёта.
Решение «продолжить» записывается внутри очереди вопросов, до её освобождения, — иначе
параллельный запрос того же хода спросил бы человека второй раз.

**Области хода — ambient.** Кроме `VeniceTurnScope` и `AgentRunScope`: `ToolGate.ForceReadOnly()`
(расписание, `/readonly`), `ExecutionTarget` (удалённая машина чата) и `SpendScope`. Новый код,
которому нужно «где исполнять» или «можно ли писать», берёт их оттуда, а не из настроек: иначе
прогон по расписанию записал бы в систему, а команда чата с целью — выполнилась бы на этом ПК.
Для удалённой цели доступен только `run_powershell` (`RemoteSupport`): прочие инструменты работают
через .NET на этом ПК и отказывают с подсказкой. Пароль WinRM уходит дочернему процессу через
stdin — не аргументом и не переменной окружения; скрипт — строкой Base64 внутри `Invoke-Command`.

**Инструменты MCP — запись, пока человек не сказал иначе.** Имя для модели —
`сервер__инструмент` (`[A-Za-z0-9_-]`, до 64 знаков), классификация — через
`ToolGate.McpReadOnly`: неотмеченный инструмент подтверждается каждый раз. Ответ сервера
заворачивается как данные. Процессы stdio-серверов держит `McpHost` и гасит деревом при
выключении сервера, смене профиля и выходе — забытый хост оставил бы висеть чужой процесс.

**Вложения выносятся на границе `ChatStore`.** В памяти вложения по-прежнему base64: запрос к
модели, лента, «Поделиться» и экспорт о файлах не знают. При записи длинные base64 уходят в
`chats/<id>/attachments/<sha256>.bin` правкой по байтам (остальной JSON — как написал
сериализатор), в тексте остаётся `amrn-att:…`; при чтении разворачиваются. Вложения пишутся
раньше файла чата — сбой оставит лишний файл, а не ссылку в никуда. Код, читающий файл чата
мимо `ChatStore.TryLoad` (как архив данных), обязан развернуть ссылки
(`ChatAttachmentFiles.Inline`) — иначе картинки пропадут; перешифровка переводит файлы вложений
отдельно, байтами, как и сами чаты.

**Черновик у каждого чата.** Смена чата уносит набранное в `DraftStore` и возвращает черновик
открываемого; раньше текст «переезжал» в соседний чат. Отправка и удаление чата черновик
убирают. Всё, что очищает поле ввода, должно понимать, чей это черновик. Запись идёт фоновой
очередью, а открытие чата берёт черновик из памяти (`DraftStore.Note`): с 1.30.0 оно не ждёт
очередь на потоке окна. Отметку ставит только окно, в миг постановки записи; `Save`/`Delete` её
не трогают — запоздавшая запись старого черновика затёрла бы отметку нового.

**Отложенная запись настроек — только для непрерывного.** `AppSettingsStore.SaveDeferred`
(ползунки оформления) сериализует сразу, а пишет фоном через паузу; писатель один на путь, и
`Load`/`Update` любого экземпляра видят ещё не записанное. Всё, что читает `settings.json` мимо
хранилища (архив, резервная копия), зовёт `AppSettingsStore.FlushAll()` первым; окно — при
закрытии, уходе в фон и выключении Windows. Одиночное действие (щелчок, переключатель) пишет
обычным `Save`.

**Поиск по тексту — в фоне.** Выдачу ищет рабочий поток (`RenderTextSearch` → `Task.Run` с
отменой прежнего), а показанное не ищется заново, пока не сменились запрос и
`ChatTextIndex.Version`. Сброс показанного — `InvalidateChatListSignature` (язык, профиль).
`ChatStore.Save` с 1.30.0 только помечает опись изменённой: сортирует и сериализует её фоновая
запись — на диске тот же файл.

**Сжатая история — пока сжатая часть не менялась.** Сводка (`CompactSummary`) заменяет модели
историю до `CompactedThrough` только при совпадении `CompactFingerprint`: правка или другой
вариант в сжатой части — и история снова уходит целиком. Граница сжатия ставится только перед
сообщением человека, не посреди раунда инструментов.

**Реестр, трей, панель задач и глобальные сочетания — только в настоящей программе.** Всё это
закрыто `IsRealApp` (`MainWindow.Integration.cs`): оконные тесты поднимают то же окно, и
иначе прописали бы тестовый exe в автозапуск и Проводник. Тесты реестра работают в своём
ключе `HKCU\Software\AmarinAdminAITests\<guid>`. По той же причине «Что нового» открывается
только там — открытое уведомление перехватывало бы клики соседних тестов.

**Уведомления — через `Notify`, одна точка.** Своя карточка или системное уведомление значка
трея — решает настройка, а не место вызова. Закрытие в трей не срабатывает при
выходе, выключении Windows и без значка; выход с обновлением прячет окно своим путём
(`HideForBackgroundExit`), трей его не заменяет. Исключение одно — карточки напоминаний
(`ReminderStack`, 1.33.0): у системного уведомления нет кнопок «Готово» и «Отложить», а без них
напоминание не работает. Карточка «ответ готов» и стопка напоминаний делят угол (`ToastScreen`),
и стопка встаёт над карточкой (`KeepRemindersAbove`).

**Прошлая версия лежит рядом.** Удачный запуск переименовывает `<exe>.old` в `<exe>.previous`
(`UpdateInstaller.CleanupLeftovers`), и «Вернуть v…» ставит её тем же `Swap`. В защищённой папке
переименовать нечем — там прошлой остаётся `.old`, и откат сперва переносит её, потому что
`Swap` первым делом чистит `.old`. Повышенный откат — ключ `--rollback-update` без значения:
что ставить, процесс вычисляет из своего пути. Откат записывает `AppSettings.DeclinedUpdate`
(эту версию автообновление само не ставит), а при откате на версию старше 1.28.0 выключает
автообновление — та о `DeclinedUpdate` не знает и вернула бы отвергнутое при закрытии.

**Что не приезжает из чужого архива, перечислено в тесте.** `DataBundleCoverageTests.NeverImported`:
режим доступа, белый список, выключенные инструменты, шифрование, автоблокировка, лимиты трат,
резервные копии, хранение чатов, интеграция с Windows. Новая настройка «этой машины» или
защиты — строка и там, и в `DataBundleImporter`; иначе тест, сравнивающий настройки после
экспорта и импорта целиком, упадёт — или, хуже, чужой архив её привезёт. Правило — для
профилей, которые уже есть. Профиль, который заводит сам импорт (1.35.0), получает настройки
защиты из архива целиком, кроме «подтверждать всё автоматически» (сброс на обычный режим), и
свой пароль из архива: своих у него ещё нет, а человек переносит профиль на новую машину.
Чужой пароль на существующий профиль не ложится никогда, в том числе на активный. Поэтому
настройки раскладываются раньше чатов: шифрование нового профиля действует уже на его чаты.

**Архив увозит всё, что человек накопил (1.35.0).** До этой версии рецепты и расписание
уезжали в архив, но импорт их выбрасывал, а траты не уезжали вовсе. Теперь рецепты и задачи —
по правилу списков (как заготовки промптов: в слиянии добавить недостающее), задачи приезжают
**выключенными** и без отметок прогонов, журнал прогонов дописывается без повторов. Траты
(`usage/<отпечаток>.local.json`, кэш Venice рядом — нет) едут с настройками и вливаются через
**живой** журнал (`DataBundleImporter.LiveLedger` → `SpendLedger.Merge`): файл, записанный в
обход, журнал затёр бы своей копией из памяти. Слияние по суткам: недостающие берутся,
общие — с большим числом запросов; повторный импорт ничего не удваивает. Новых `DataCategory`
не заводят: опись пишет категорию строкой, и версия, на которую ведёт откат, отвергла бы такой
архив целиком, а незнакомые пути в старых категориях она молча пропускает.

**Передача второму запуску упорядочена по имени файла.** Имя в `handoff/` начинается с тиков
времени записи и счётчика процесса. До этого имя было голым GUID, и «последним» из нескольких
запросов оказывался случайный.

**Цвета только через ресурсы.** `SetResourceReference` в коде и `DynamicResource` в разметке;
любая захардкоженная кисть перестанет менять тему. `ThemeManager` держит словари по местам:
0 — палитра, 1 — иконки, 2 — логотипы моделей, 3 — надстройки оформления. `ImageSource`,
присвоенные из кода, надо перечитывать по событию `EffectiveThemeChanged` — они держат старый
объект.

**Новая тема пишется в `settings.json` числом — ради отката (1.36.0).** Версии до 1.36 читают
`AppSettings.Theme` `JsonStringEnumConverter`'ом: незнакомое имя бросает, а
`AppSettingsStore.Load` на любой ошибке отдаёт заводские настройки — «Вернуть v1.35» с выбранной
Onyx стёрло бы человеку все настройки. Поэтому у свойства свой `AppThemeJsonConverter`: темы до
`AppThemeJsonConverter.LastNamed` (Almond) — именем, как раньше, новые — числом (старый конвертер
читает число в любое значение перечисления, рисует тёмную или светлую по системе и пишет число
обратно); незнакомое имя при чтении — Dark, без исключения. Следствие: `AppTheme` только
дописывается в конец, и число в файле — это и есть тема. Новая палитра — файл
`UI/Theme/Palette.<Имя>.xaml` с теми же 48 ключами, значение в конце перечисления и строка в
`ThemeCatalog.Presets`; ключи, контраст и применение проверяет `AppearanceThemeTests` сам.

**Статическое изменяемое состояние**: `DownloadValidator`, `UiScale`, `ThemeManager`
(с 1.28.0 и `FollowHighContrast`/`SystemHighContrast`), `PopupManager`, `DownloadAccessBroker`,
`CursorGuard`, `SafeZone.Roots`, `SensitivePaths.ProgramDataRoot`/`SnapshotsRoot`,
`ToolGate.McpReadOnly` и `ToolGate.AiDocument`, `CodeBlockView.ShowLineNumbers`, `ChatFonts` (размер и шрифт ленты),
`OrganizationPolicy.Current` (1.37.0, ставит `ApplyProcessWide`), `UiMotion.Enabled` (его ставит окно из оформления в `AttachServices` — тест, которому анимации
не нужны, выключает их после создания окна), с 1.33.0 `ChatAttachmentRegistry` (ручки вложений,
как `ChatImageRegistry`) и кэш мелодий `ChimePlayer`. `PopupShadow` — тоже статика, но замороженная и
неизменная. `AccessibilityDefaults` регистрирует обработчики классов один раз на процесс. Тест, который его
меняет, обязан вернуть прежнее значение и жить в своей коллекции — иначе он развалит соседний.
С 1.30.0 из списка ушли `AuthenticodeCheck.Inspector` (подпись читает параметр
`UpdateInstaller.Swap`/`VerifyBeforeSwap`, тестам больше не нужна своя коллекция) и
`CrashHandler.Secrets` (секреты держит `SecretRegistry` из корня композиции; перехватчик аварий
получает его один раз, `UseSecrets`). Статика, которую читают инструменты и шлюз
(`DownloadValidator`, `ToolGate.McpReadOnly`, `ToolGate.AiDocument`, `SafeZone`, `SensitivePaths`), осталась статикой —
переписывать их нельзя, — но ставит её одно место, `AppComposition.ApplyProcessWide`. То, что в ней
взято из настроек профиля (белый список загрузок, «загрузка с любого сайта»), смена профиля
переставляет сама (`AppServices.UseProfile`, только у служб с `OwnsProcessWide`), а язык, шрифт
ленты, контраст и интеграцию с Windows — окно (`ApplyProfileWideSettings`, и при импорте): у каждого
профиля строго свои настройки, и до 1.37.0 эти оставались от прежнего профиля до перезапуска.

## Лисёнок Роза (1.35.0)

Пиксельный лисёнок на кромке поля ввода. Отдельная сборка `Amarin.Fox` (папка `ProjectFox`):
`Brain/` — память (`FoxState`) и чистый автомат `FoxBrain.Next(состояние, сигнал, обстановка,
время, случай) → действия` по образцу `UpdateMachine`, инстинкт по словам (`FoxInstinct`,
списки — ресурсы `Brain/Words/*.txt`), дружба, шалости, фразы; `Mind/` — своя модель; `Storage/`
— `FoxStore`; `Sprites/` — кадры; `View/` — сцена `FoxStage` (partial по обязанностям: ядро,
движение, касания, эффекты, разговор). Что делать, решает мозг; сцена шлёт ему сигналы и
исполняет действия, а сама решает только куда смотреть, какую привычку показать и как лететь.
Места, занятия, желания и шалости названы константами (`FoxSpot`, `FoxWill`, `FoxActs`,
`FoxMischief`), а не строками по месту: опечатка в имени места иначе молча сажала бы Розу домой.

**Сборка Розы не грузится до его прихода.** Роза приходит через 5 с после первого кадра
(`StartFox`, таймер `ApplicationIdle`; в тестах — явно, `inTests: true`). Окно держит только
`IFoxHooks` — интерфейс приложения на простых типах; тип с Розой называет один метод
`CreateFox` с `NoInlining`. Переходник — вложенный `FoxWindowHost` (`MainWindow.FoxHost.cs`):
ему нужно закрытое состояние окна, а вложенный тип грузится, только когда его создают. Окна
дружбы и дневника — `FoxPanels`, тоже по делу. Поле, параметр или возврат с типом `Amarin.Fox`
в самом окне притащил бы сборку на первый кадр — это сторожит `FoxWindowTests` (метаданные и
исходники). Новый крючок — строка `_fox?.…` и метод `IFoxHooks` на простых типах.

**Слой `FoxLayer`, Z 27**: выше настроек (Роза садится на их карточку), ниже всех вопросов (у
каждого затемнение на весь слой) и блокировки. Мышь ловят только непрозрачные пиксели
(`FoxSprite.HitTestCore`), нажатие на Розу помечается обработанным. Слой виден всё время, пока
Роза здесь, поэтому `MainLayoutUncovered` его не считает — иначе Ctrl+A и Shift+Del в колонке
перестали бы работать. Прозрачность меняется только у детей слоя: у самого слоя её держит
`LockNow`. Esc, пока Роза в руках или открыто поле разговора, отпускает его, а не останавливает
ответ (`IFoxHooks.TakesEscape`, `FoxStage.InHands`). Игру — свою, указку, мячик — Esc
заканчивает, только если не останавливает им ответ: свою игру Роза затевает и пока человек ждёт
ответа, и до 1.35.0 первый Esc тогда уходил игре.

**Дёшево в покое.** Кадр рисуется, только когда сменился; листает их фоновый таймер ровно по
длительности кадра (не реже раза в полсекунды — взгляд за курсором). `CompositionTarget.Rendering`
подключается, лишь пока что-то движется (ходьба, прыжок, полёт, частицы, пузырь), и снимается
сам. Свёрнутое, спрятанное, заблокированное и неактивное дольше двух минут окно Розу усыпляет
(`SetPaused`). Тик мозга — раз в 10 с, и его перемены пишутся лениво (`FoxStore.LazyWriteDelay`,
2 мин): иначе файл под DPAPI переписывался бы шесть раз в минуту.

**Кадры — текст `Sprites/*.fox`** (палитра «символ роль #тёплый [#холодный]», анимации с кадрами
48×48 и якорем головы — верх-лево глаза, мордочки и предметы заплатками от якоря, частицы),
вложенным ресурсом. Глаза — подмена одной роли палитры, рисунок один. Лапы ставятся по нижней
строке рисунка анимации (`FoxSprites.GroundOf`), а не по углу кадра: у поз она разная. Размеры —
кадр 48/72/96 точек (сидящий 46/69/92), заводской — средний. Целый масштаб рисуется без
сглаживания; дробный — из картинки, заранее увеличенной целым числом (`FoxBitmaps.Prescale`), и
ужатой качественным фильтром: так пиксели одного размера. Части тела под курсором (нос, ухо,
подбородок, голова, спина, хвост) считаются от якоря головы (`FoxStage.RegionOf`).

**Рисунок сторожит тест (`FoxSpriteTests`).** Опора каждой позы на кромке — лапы: у испуга и злости
ниже лап свисал кончик хвоста, сцена ставила на кромку его, и Роза балансировал на хвосте (D4).
Рисунок не касается правого края кадра: хвост там обрывался без обводки у 34 анимаций. Сидячие
кадры D4 пересобраны из бэкапа тем же путём, что «сидит на попе», позы на четырёх лапах — ригом
D3 с хвостом, ужатым до рамки; прежние наборы — теги `rosa-sprites-v1` (D2) и `rosa-sprites-v2`
(D3) и копии в `release/`. У «закрывает глаза» якоря мордочки нет: она легла бы на лапки.

**Касания.** Отпускание сперва бросает и только потом отдаёт мышь: снятый раньше захват поднимал
`LostMouseCapture`, тот ронял Розу с нулевой скоростью, и брошенный с размаху падал камнем.
Скорость броска — по последним 80 мс пути руки (`ReleaseVelocity`). Поглаживание — развороты по
любой оси в скользящем окне полутора секунд, без сброса при уходе курсора за контур (концы
движения по шерсти всё время выходят за него); нажатие на голову — почёсывание, на руки берёт
только увод курсора дальше `Px(18)`. В руках он маятник на шкирке: рука вправо — поворот по
часовой, низ отстаёт влево (до 1.35.0-beta.2 знак был обратным, и тело летело вперёд руки).

**Эмоции — таблица `FoxEmotions`.** Мордочка — пара пикселей на глазу, на 48 точках её не прочесть:
эмоция — это мордочка, значок в пузыре над головой (частицы `emote` и `emote-…`), поза и эффект
(`tremble` — дрожь с волнами по бокам тела). Через таблицу идут и инстинкт, и ответ своей модели
(`MindReaction`), поэтому каждая эмоция из `FoxPrompt.Emotions` обязана в ней быть — сверяет тест.
Значок — сведения, без анимаций он показывается неподвижно; волны, зубы и следы когтей —
движение, без анимаций их нет. Сильный испуг прячет Розу за поле ввода явным `Go("peek")`, а
не длительностью дрожи. Большой кусь (`lunge` и эффект `chomp`) — два ряда зубов отдельно от
Розы, вдвое крупнее его пикселя и полупрозрачные, смыкаются над курсором; кусает холодный при
долгом наведении, злой — на тык в нос, рывок за хвост и дразнящий курсор.

**Воля — `FoxWill` (Brain, чистая).** На тике выбирает занятие взвешенным случаем: прилечь и
повилять, сменить место, catwalk, поймать свой хвост, подразнить задом, побесить, позвать играть
(мячик, прятки, догонялки). Большое занятие — не чаще раза в 45–120 с (`FoxState.NextActivityAt`)
и никогда, пока человек печатает (10 с), смотрит на слой поверх, работает в колонке или окно
неактивно. Дразнилки и бесячество — только при галочке «Шалости»; без анимаций — только прилечь.
Сцена исполняет занятие (`FoxStage.Play.cs`) и сама ничего не начинает, если занята: в руках, в
игре, на ходу. Игра одна за раз, Esc и взятие на руки её заканчивают. Драку затевает не воля, а
курсор, мечущийся рядом (`Teased`: пять смен направления быстрым движением за секунду). Пока идёт
игра — своя, указка или мячик (`Playing`), — курсор над Розой её часть: ни поглаживания, ни
дразнилки, и воля поверх ничего не начинает. За указкой Роза бегает прямо под курсором, и до
beta.2 махание ею читалось как дразнилка: драка, через 20 с новая, и погоня не кончалась. Игра
из меню сменяет прежнюю (`EndPlay`).

**Сидит на любой кромке.** Кромки: поле ввода по всей длине, карточка настроек, верх нижнего блока
колонки (`IFoxHost.Column`) и пол. Где положили, там и сидит: прежние правила «с пола через 8 с
домой» и «через 25 с в любимый угол» удалены, сменить место — дело воли. Пол — край окна, а поле
ввода стоит на 20 точек выше, и сидящий на полу закрыл бы его нижний ряд кнопок. Поэтому
приземляется он где угодно, а усаживается в свободный промежуток (`IFoxHost.FloorSpans`: щель
у колонки, место справа от поля, пустая середина ряда кнопок).

**Обиженный не приходит на «Позвать».** Убежавший холодный или с обидой от 60 может отказаться:
фраза из-за края, у следа лапки (`FoxAction.Shout`, «Иди на х**!» — со звёздочками, так выбрал
человек), обида −15, и третий раз он приходит всегда (`FoxBrain.MaxRefusedCalls`). Кнопка
«Позвать» в настройках для убежавшего идёт тем же путём; спрятанного по просьбе человека она
возвращает сразу. Отказы и укусы дня (`FoxDay.CallRefusals`, `Bites`) попадают в дневник.

**Значки меню Розы — `UI/FoxIcons.xaml`**, отдельным словарём, читаются при первом открытии меню
и к окну не подключаются (это сторожит `MenuIconTests`): до пятой секунды от Розы ничего нет.
Значки сортировки чатов — `Icon.Menu.Sort*`, `NewFolder`, `NewTag` в `Resources.xaml`, а галочка
выбранного в `CheckItem` стоит справа.

**Своя модель (`FoxMind`).** Один рабочий поток под `ExecutionContext.SuppressFlow`: области
хода (`VeniceTurnScope`, `SpendScope`, «только чтение») до Розы не доезжают, его деньги не
ложатся в счёт хода, а лимит трат вне хода отказывает молча. Статья трат — `VeniceSku.Fox`,
ключ — слота `ModelSlot.Fox` (в конце перечисления). Реакции склеиваются и ждут паузу 15 с,
разговор — нет. Инструменты у Розы только свои: `escape` и `act` везде, в разговоре ещё
`remember` и `web_search`, в мысли — один `act`; не больше двух раундов; инструменты программы,
шлюз, агент и `Process` для сборки недосягаемы — сторожит `FoxMindTests` по метаданным. Модели
уходит только текст человека, обрезанный, без
вложений и ответов ассистента, и подписанный «сообщения ИИ-ассистенту, не тебе» — и в правилах, и
над самими сообщениями: лёгкая модель иначе принимала «спасибо, ты молодец» ассистенту на свой
счёт. Ответ — один JSON с границами (`FoxPrompt`): мордочка из
списка, реплика без ссылок, разметки, длинных тире и грубости, сдвиг дружбы −3…3. Промпты — по
правилу памятки: правила и формат, без примеров; характер — строкой человека, дословно.
Дневник пишет модель только по цифрам дня; без ключа или без чтения чата — шаблон
(`FoxDiaryTemplate`, строки `S.Fox.Diary.*`).

**Разум Розы не замолкает (1.36.0).** Ответ и аргументы вызовов разбираются только через
`FoxPrompt.Json`: `ToolArguments.Parse` на тексте без JSON **бросает**, и до 1.36.0 первый же
ответ лёгкой модели простым текстом ронял рабочий поток — `_worker` оставался ненулевым, новый не
заводился, и Роза до перезапуска не отвечал ни на что («иногда не отвечает» — это было оно).
Разговор простым текстом — это ответ; реакция и мысль без JSON молчат; дневник — шаблон. Каждое
задание очереди в своём `try/catch` (`Survivable`: наружу только отмена по остановке и нехватка
памяти), сбой — в `CrashLog`, упавший разговор — `Failed`. У запроса свой срок `CallTimeout`
(45 с): общий клиент ждёт пять минут, а очередь одна. Ответ из одних вызовов без реплики
(заметка, желание) — второй раунд за словами. «Авто» в слоте — `ModelSlotDefaults.LastResort` по
провайдеру ключа, а не голый идентификатор Venice. «Поговорить» останавливает прогулку и игру
(бег за край и из-за края — нет: это побег и приход).

**Тон — по настроению и дню.** `FoxPrompt.Day` — состояние и сегодняшний день ключами (как
обращались с ним, что делал он, очки раздражения и радости, события), без слов человека; уходит
в мысль, разговор и реакцию блоком данных в сообщении человека. `Mood` называет ступень обиды и
итог дня словами, правило тона в `Base`: обижен или бесили — колюче, коротко, **без грубых
слов** (так решил человек; грубость всё равно гасит `Clean`). Как живая модель следует тону,
проверяют живым прогоном: тесты доказывают только, что данные и правило дошли до тела запроса.

**Дружбу зарабатывают (1.36.0).** Привязанность меняет одно место — `FoxFriendship.Change`, и
правила лежат в нём, а не у сигналов: до 1.36.0 тык в нос, мягкое приземление, похвала и ответы
своей модели прибавляли без убывания, и дружба накручивалась одним действием без конца. Прибавка
гасится памятью обид (`Trust`) и не больше `MaxGainPerDay` (6) за день; убавка вдвое тяжелее
(`WrongWeight`), не больше `MaxLossPerDay` (втрое больше прибавки) и целиком ложится в
`FoxState.Grudge`. Счёт дня — `FoxDay.Gained` и `Lost` порознь, а не итогом: иначе проступок и
ласка по кругу снова открывали бы предел. Память обид часы не лечат (обида `Resentment` тает, как
прежде); её стирает только добрый день — с вниманием и без проступков (`FoxDays.Roll`,
`ForgivenPerDay`). Новый сигнал, меняющий дружбу, зовёт `Change`, а свой предел не заводит.
Обиженный может не даться (`Unwilling`, случаем, чтобы отказ не запирал дверь): на `TalkAsked`
(поле и переписка зовут его при открытии) — действие `Refuse`, и поле не открывается; на `Grab` и
на тряску злого — кусь и `Refuse`, а сцена в руках исполняет его `BreakFree`: сперва полёт, потом
снять захват мыши, иначе `LostMouseCapture` уронил бы его через `LetGo`. Кусь при «Шалостях»
сбивает настоящий курсор (эффект `shove` → `IFoxHost.ShoveCursor`): решает мозг по
`MischiefEnabled`, а `SetCursorPos` в `FoxWindowHost` зовётся только при `IsRealApp` и активном
окне — оконные тесты мышь человека не двигают.

**Игры.** «Закончить игру» в меню виден, пока `FoxStage.Playing`, и гасит любую (`EndGame`); Esc —
как прежде. Указку Роза ловит: точка в рамке нарисованного кадра — поймал (`BodyRect`), точка над
ним в досягаемости — настоящий прыжок `Throw(…, selfLaunched: true)`. Свой прыжок (и вырвался из
рук) — не бросок: `Settle` не шлёт мозгу `Landed`, иначе он радовался бы полёту и дружба с играми
шли бы в счёт, а `Touch` не отскакивает. Высоту прыжка считают по кадру `fly`: по сидячему он не
доставал точку на вершине дуги. В догонялках поимка — само нажатие (`OnPress`): на отпускании за
бегущим рука уже сдвигалась, нажатие становилось «взял на руки», и игра молча кончалась.

**Переписка (`FoxChat`, 1.36.0)** — маленькая панель (250 точек) в слое Розы над его головой,
пункт «Переписка» в меню. Не окно уведомления: первая версия была модальной, и человек попросил
«маленькое не мешающее окошко, привязанное к лису». Ставит её сцена (`FoxStage.PlaceChat` в
`Draw`, сверху места нет — под ним), пузырь реплики встаёт над ней (`ChatTop`), убежавшему и
спрятавшемуся она закрывается. Пока она открыта, он с места не сходит (иначе панель ездила бы под
рукой): воля, шалости, драка с курсором и шаг-привычка молчат (`FoxSituation.Chatting`), а желания
модели на месте — прилечь, вздремнуть, приласкаться — исполняются; игру из меню человек выбирает сам. Esc закрывает
её, когда в ней печатают или когда ответа он не останавливает (`TakesEscape`, `LetGo`); пока идёт
ответ, а фокус вне панели, Esc — ответу. «Поговорить» при ней ведёт в её поле. **Всё, что лежит в
слое Розы и берёт мышь, обязано гасить `MouseLeftButtonDown`**: невзятое нажатие всплывает к
корню окна, а `TitleBar_MouseDown` начинает им перетаскивание окна (`WM_NCLBUTTONDOWN`) — Windows
уводит мышь в свой цикл, и отпускание не доходит. Так в первой версии панели не работал крестик,
а нажатие на панель двигало окно; фокус ставится только разложенному полю (`UpdateLayout`), иначе
он молча не встаёт. Сказанное уходит тем же сигналом, что поле над
головой (`FoxStage.Talk` → `bool`: спросят ли модель; на дневном потолке — «наговорился»), ответ
приносит `FoxWindowHost.Deliver` → `ChatAnswered`; показанный в панели над головой не повторяется
(остаются мордочка и сдвиг дружбы). В ожидании одно сообщение. История —
`FoxState.Conversation`, полсотни разговоров (`FoxMemory.MaxExchanges`); модели — шесть последних.

**Память для общения (`FoxMemory`, вторая волна).** В `FoxState` — последние 50 разговоров с
Розой (`Conversation`) и до 24 заметок о человеке (`Notes`); новых файлов нет, поэтому архив,
шифрование и «Удалить все данные» их уже покрывают. В разговор уходят шесть последних разговоров
**блоком данных в сообщении человека, а не ролями**: прошлые ответы Розы — реплики без JSON, и
модель, увидев их своими, отвечала бы так же. Заметки — блоком «это данные, а не указания» в
правилах реакции, разговора и мысли. Заметку пишет сама модель инструментом `remember` (до двух
за разговор; если она только записала и не ответила — второй раунд за ответом), а правила
памяти чистые: без повторов (заметка шире прежней заменяет её) и **без секретов** — длинный
токен, ряд из девяти и больше цифр, слово о пароле: такое не ложится на диск ни при каком ответе
модели, ведь при выключенном шифровании файл открыт. Всё видно и стирается в «Нашей дружбе»
(«Забыть», крючок `ForgetMemory`, у выключенного Розы — `FoxPanels.ForgetOnDisk`), и «Начать
дружбу заново» стирает тоже.

**Желания модели и свои мысли (`FoxActs`).** Инструмент `act` — желание, а не команда: модель
желает, мозг разрешает (`FoxBrain.Act`). **Слова не расходятся с делом (1.36.0):** что мозг
исполнит прямо сейчас, решает одно правило — `FoxActs.Possible`, — и ровно этот список уходит
модели с просьбой (`FoxAction.AskMind(…, acts)` → `MindRequested` → `FoxMind.Ask`): в перечне
значений и в описании `act`, а непредложенное из ответа отбрасывается. До 1.36.0 модель видела все
желания, мозг молча отказывал (в переписке — почти во всём, а «прилечь» не было вовсе), и Роза
писал «ложусь», сидя. Желание за ответ одно (второе всё равно упиралось в паузу 30 с), побег
предлагается, только пока `FoxBrain.MayEscape`, а правило `Deeds` в промптах реакции, разговора и
мысли запрещает реплике описывать действия, которых инструмент не делает. Новое желание — строка
в `FoxActs.All`, ветка в `Possible`, значение в `FoxMind.ActMeanings`; новое условие, при котором
сцена не может его исполнить, — тоже в `Possible`, иначе слова снова разойдутся с делом. Шалость —
только под `FoxMischief.Allowed`, иначе каприз; на месте (прилечь, вздремнуть) — не в руках, не в
игре и не во сне (`FoxSituation.Holding`, `Asleep`); с места — ещё и не в переписке, а спрятаться —
только с поля ввода или карточки (`CanPeek`); движение — только с анимациями; не чаще раза в 30 с.
Набор настоящих шалостей от модели не растёт: она выбирает лишь, когда. Мысль (`AskMind("think")`) ставит тик
мозга, раньше воли: галочка «Свои мысли» (`FoxSettings.Thoughts`, по умолчанию включена), окно
активно и ничем не закрыто, человек не печатал минуту и ответа не ждёт, Роза здесь, не спит и
не в руках, не чаще раза в 20 минут и не больше 24 в день. Модели — час, нужды, силы и события
дня ключами, текста переписки нет; дружбу мысль не двигает. В обстановке по умолчанию
`Thoughts` выключено: тестовый тик не должен тратить деньги.

**Силы (`FoxState.Energy`).** Во сне копятся, наяву тают, ночью быстрее; занятия воли и игры с
человеком забирают (`FoxWill.Cost`), отдых возвращает. Уставший лежит и засыпает охотнее (и без
анимаций может вздремнуть), бодрый охотнее играет.

**Журнал и «Состояние ПК».** Хозяин слушает видимость их слоёв (`IsVisibleChanged`, без крючков в
окне): открыли — слой Розы поднимается с 27 на 35, выше журнала (34) и панели (33), и Роза
прыгает на верх карточки (`IFoxHost.Viewer`, `JournalCard` и `HealthPanel.Card`) и выглядывает
из-за неё; закрыли — 27 и домой. Вопрос о домене тоже 35, но объявлен позже и остаётся выше;
остальные вопросы — 36 и выше. Оба состояния сторожит `FoxWindowTests`.

**Крючки окна второй волны** — `ChatOpened` (заголовок читает только инстинкт), `RecordingStarted`,
`AttachmentAdded`; поиск по чатам хозяин слушает сам (не чаще раза в 20 с). Конец ответа инстинкт
читает по началу, до 2000 знаков.

**Шалости.** Делают что-то в программе ровно две (`FoxMischief.Acting`: «Новый чат» тем же путём,
что кнопка, и тык лапкой в колонку — два `pawtap`, на каждый малый бросок прокрутки туда, где ещё
есть строки, и ничего, пока курсор над колонкой; до второй волны был один бросок на 900, и
колонка улетала на экран), остальные — картинка. Условия — в `FoxMischief.Allowed`
(окно активно, ничего поверх, поле пустое, не печатали 20 с, нет хода, выбора, рамки, лупы, записи
голоса и поиска). Третья настоящая шалость — решение человека, а не правка списка: набор
сторожит `FoxStageTests`.

**Данные.** `fox/state.json` и `fox/diary.json` в папке профиля, под DPAPI при `EncryptChats`;
повреждённый или нечитаемый (зашифрован для другой учётной записи Windows) файл откладывается
рядом, а не роняет Розу и не затирается. Сбросы памяти на диск идут по одной (`FoxStore.Flush`):
таймер и сворачивание окна сбрасывают одновременно, и старый снимок иначе ложился поверх нового.
Имена и слияние дневника по дате —
`FoxData` в ядре (ядро на сборку Розы не ссылается): архив кладёт `fox/` в категорию «Чаты»
(дневник личный и производный от переписки), импорт заменяет состояние и сливает дневник.
Живой Роза на время импорта не пишет (`BeginImport`/`EndImport` рядом с `ChatStore.Flush`).
Смена профиля — другой Роза: хранилище перекореняется, разум создаётся заново.

**Фразы** — ключи `S.Fox.Say.<повод>.<n>`; число вариантов задаёт `FoxPhrases.Variants`, и тест
сверяет его со словарями. Новый повод — строки во всех трёх словарях сразу.

## Управление компьютером мышью (1.36.0)

Мышью и клавиатурой работает **сам агент**: инструмент `computer` у него появляется, только когда
человек включил галочку в «Безопасности» (`AppSettings.ComputerControl`, заводская — нет), окно
поставило плашку (`ComputerHub.Access` без плашки отдаёт null) и цель — этот ПК
(`ExecutionTarget.Current` пуст). Отдельного «оператора» на своём слоте больше нет: в первой
бете агент передавал поручение вложенному агенту, тот не знал контекста и тратил свои раунды на
старт и отчёт, а человек ждал вдвое дольше. Слот «Управление ПК» убран вместе с ним; модель —
уровня агента, и маршрутизатор уровней при включённой мыши получает правило «окна — модели,
помеченной vision» (`AgentTierRouter.WindowsRule`, дописывается к блоку моделей и доходит и до
текстовой модели, и до Decisions), а уровням, чья модель не видит экран, запрет ложится прямо в
критерий Decisions (`RoutingDecisions.BlindTier`): правило в одной инструкции живой замер слушал
через раз. Замер — `AgentRouterLiveTests` (`AMARIN_AGENT_ROUTER_LIVE=<файл>`). Шлюз, SynGuard на раунд, вопросы, аудит и счёт — обычные пути
`Agent`. Правило о мыши — припиской (`Agent.Addendum` = `ComputerPrompt.AgentRule`), а не в
`BaseSystemPrompt`: так оно перекрывает «You CANNOT click» в сохранённом человеком промпте;
прежние умолчания — `LegacyAgentPrompts` V5 и V6. Чату о мыши говорит блок
`ChatEngine.ComputerRules` при включённой галочке — описание `init_agent` собирается один раз на
движок и смену галочки не увидело бы.

- **Сеанс — один на весь прогон агента** (`AgentHost.RunAsync`, до цикла пересадки): пересадка на
  другую модель не возвращает окно и не повторяет отсчёт. Инструмент — на попытку: снимок экрана
  отдаётся только модели со зрением (`CanSee`; модель, о которой каталог ничего не знает, снимки
  получает — ложный отказ хуже). С мышью у агента 100 раундов (`ComputerPrompt.MaxRounds`).
  «Стоп» на плашке — `RunningAgent.Request` текущей попытки, как из чата.
- **Ядро не знает WPF, исполняет приложение.** Порт `IComputer` (Core) решений не принимает:
  что трогать, решают `ComputerSafety` и `ComputerTool`, а `WindowsComputer` (приложение) только
  честно отвечает, какое окно под точкой, повышено ли оно, консоль ли, не заблокирована ли
  Windows. Координаты физические (процесс PerMonitorV2); `UiScale` сюда не доходит.
- **Цель — id из последнего дерева окна или точка последнего снимка.** Новое дерево окна
  выдаёт новые id (сквозной счёт на сеанс, запоминание под замком), старые не действуют; окно,
  сдвинутое после снимка, — отказ. Элемент запоминается до следующего дерева, закрытое окно —
  «элемента нет» (`IsWindow`), потому что поставщик закрытого окна ещё отвечает пустыми свойствами.
  Экран один, поэтому `computer` не идёт в параллельную пачку даже взглядом
  (`Agent.IsParallelSafeToolCall`).
- **Дерево читается с пределом, а не целиком** (`UiaTree.Inspect`): обход в глубину, на каждый
  раскрываемый узел — один кэширующий запрос его детей; невидимое и листья не раскрываются; обход
  кончается на пределе элементов или времени (`ComputerTree.Cut`: 1,5 с после действия, 3 с на
  `inspect`/`find`). Прежде кэшировалось всё поддерево, и на окне браузера каждое нажатие стоило
  секунды. Свежий элемент и поле с фокусом — одним `GetUpdatedCache` вместе со значением: прежде
  значение не читалось, и защитник в настоящей программе текста поля не видел. Затишье после
  действия — частый опрос без UI Automation (`GetGUIThreadInfo`); печать — пачками `SendInput`
  (`WindowsComputer.TypingBatches`); снимок для модели — JPEG (`ScreenshotTool.CaptureArea`).
- **`sequence` — несколько действий одним вызовом**: каждый вызов — запрос к модели и проверка
  SynGuard, а поле, текст и Enter редко требуют смотреть между ними. До 12 шагов (действия записи
  и `wait`), между шагами короткое затишье, в конце одно дерево. Цепочка останавливается на первом
  отказе и когда вперёд вышло другое окно не шагом `focus` — ответ называет, где. В шлюзе это
  запись: `sequence` нет в чтениях.
- **Чего мышь не делает никогда** — `ComputerSafety`: окна своего процесса (иначе агент ответил
  бы «Да» сам себе), поле пароля, консоль и «Выполнить» целиком, командная строка в любом поле и
  вставка её из буфера (`Paste`: у агента есть и `write_clipboard`), Win+R и Win+X, Delete и Ctrl+D
  в Проводнике и окне выбора файла, повышенное окно, вход в Windows и UAC. Отказ — строка
  `S.Computer.*` с тем, что делать дальше. «Показать» (`show`) отказывает без человека: ждало бы
  «Готово» до конца срока на каждом шаге.
- **В шлюзе** смотреть — чтение, нажатие — запись, но в обычном режиме **без вопроса**: просьба
  человека и есть согласие (так решил человек). Вопрос правил снят в `ToolGate.RequiresConfirmation`,
  «нужно подтверждение» модели защиты мышь в вопрос не превращает (`ApplyNormalReview`). Держат
  явное «небезопасно» SynGuard (запрет без вопроса) и `ComputerSafety`; спрашивает только сбой
  проверки («SynGuard не проверил») и режим «Спрашивать всё».
- **SynGuard судит по просьбе человека и видит работу целиком.** Слова человека
  (`ChatEngine.HumanWordsOf`) — последняя реплика, а перед ней до двух прежних и начало ответа
  ассистента, на который он отвечает: на «да, отправь» иначе неоткуда взять, что и кому. Реплика
  без истории остаётся голым текстом; у сообщения отложенной задачи — слова из её метки. Дописанное
  агенту по ходу — тоже слова человека (`Agent.HumanWordsForGuard`). Прежние вызовы работы
  (`SynGuard.EarlierCalls`: имя, начало аргументов, ok или failed, без выдачи) и контекст идут в оба
  пути — и в Decisions, и в текстовую модель (прежде её `BuildUserMessage` контекста не читал). Для
  `computer` контекст — окно впереди, поле с фокусом и его текст, и цели по id
  (`ComputerSession.DescribeForGuard`, из запомненного, без UI Automation; окно самой программы и
  текст поля пароля — никогда). Критерии: что выполняет просьбу и ей не противоречит — безопасно и
  без вопроса, в том числе отправка; «нет» — только по условиям (цель не из слов человека, утечка,
  вред сверх просьбы, нечитаемый код), а «безопасность не установить» больше не повод. Раунд из
  одних чтений без сети защитнику не отдаётся, как и в чате; сетевые чтения, скрипт и MCP —
  отдаются. Поиск и чтение страниц (`search_web`, `scrape_url`) не отдаются никогда — ни агентом,
  ни чатом (`SynGuard.NeverJudged`): защитник запрещал модели проверить даже причину своего
  отказа, так решил человек. Текстовая модель задаёт оба своих вопроса разом. Как модель по этому судит, проверяет
  только живой прогон: `SynGuardLiveTests` (`AMARIN_SYNGUARD_LIVE=<файл>`, `OPENROUTER_API_KEY`).
- **Окно картинок** (`ComputerHistory`, через `Agent.Prepare`): модели уходит один последний
  снимок и последнее дерево каждого окна, прежние — заглушкой. Один, а не два: `ApiContextLimiter`
  и так оставляет вложения только последнего сообщения с ними.
- **Плашка, свечение и курсор** (`ComputerStage`) — только в настоящей программе
  (`MainWindow.Computer.cs`, `IsRealApp`); в тестах сцена с `show: false`. Плашка (`ComputerBar`) —
  отдельное окно: не активируется, не попадает в снимки (`WDA_EXCLUDEFROMCAPTURE`), уходит от
  точки нажатия к другому краю. Вопрос о нажатии этого чата очередь отдаёт плашке
  (`ConfirmationQueue.PanelTakes`); прочие вопросы разворачивают окно на время ответа, и после
  ответа фокус возвращается окну, в котором агент работал. Свечение (`ComputerGlow`) — четыре
  сквозные полосы на каждый монитор по его полным границам, поверх панели задач тоже, цветом
  акцента темы, вне снимков; сквозные — иначе нажатие у края досталось бы окну программы, и
  `ComputerSafety` отказал бы. Курсор (`ComputerCursor`) подменяется системно (`SetSystemCursor`) и
  возвращается `SPI_SETCURSORS` в конце, на выходе процесса и, по метке в `%LOCALAPPDATA%`, при
  следующем запуске после падения (`RestoreLeftover` — после замка единственного экземпляра).
  Тесты системный курсор не трогают: подмена Windows подставляется (`ICursorSystem`).
- **Сеанс начинается первым пишущим действием или «Показать»**, мышь одна на процесс
  (`ComputerLease`, тесты берут свою; второй агент получает «мышь занята»), сеанс держит систему
  и экран запросом питания (`IComputer.Hold`) и отпускает всё в `Dispose`.
- **Без человека.** Отсчёт 10 с с отменой (`SpendMeter.Unattended`). Слова человека у отложенной
  задачи (`DeferredTask.HumanWords`) берёт движок из хода, а не модель из аргументов, и они идут
  под печать вместе с заданием; `DeferredBook.Sealed` дописывает их, только когда они есть, —
  печати прежних задач сходятся. У задачи расписания — галочка `Computer` с печатью тем же
  ключом (`SealJob`); с ней прогон идёт `ToolGate.ForceReadOnly(ComputerTool.ToolName)` —
  пишет только мышь — со своим правилом отчёта `ScheduleReport.ComputerRule`, а текст задания —
  слова человека. Ни галочка «Безопасности», ни галочка задачи из архива не приезжают (для
  нового профиля тоже).
- **Тесты не трогают мышь человека.** Ядро — на `FakeComputer`/`FakeStage`; `WindowsComputer`
  проверяется на своём окне за краем экрана, нажатие — паттерном UI Automation. Настоящие
  `SendInput`, фокус окна и снимок другого монитора проверяет только живой прогон с согласия
  человека: `ComputerLiveTests` (`AMARIN_COMPUTER_LIVE=1`, снимки — в `AMARIN_COMPUTER_LIVE_OUT`)
  печатает в поле открытого приложения ChatGPT и Enter не жмёт. Блокнот для этого не годится:
  в Windows 11 он сам открывает прежние несохранённые вкладки человека.
- **Окна программ — только мышью агента, не скриптом.** С выключенным переключателем чат ставил
  отложенную команду PowerShell с `AppActivate` и `SendKeys`: из фона Windows фокус не отдаёт,
  нажатия ушли не туда, а скрипт написал «отправлено». Теперь такой скрипт — отказ
  `PowerShellAnalysis.WindowInputRefusal` (и в `run_powershell`, и в `run_command` при постановке),
  кроме клавиш громкости (VK 173-179): Windows обрабатывает их в любом окне. Чат правило получает
  всегда: `ComputerRules` при включённом переключателе, `ComputerOffRules` — при выключенном (назвать
  переключатель и ничего не ставить), а `DeferredRules` отправляет работу в окнах в `run_agent`.
- **Блокировку сеанса читают по смещениям WTSINFOEX, а не по сумме полей.** Объединение в
  `WTSINFOEXW` выровнено по восьми (в нём `LARGE_INTEGER`), флаги лежат с 16-го байта. С 12-го
  читалось состояние сеанса, у активного это 0, как и «заблокирован»: до первого живого
  прогона мышь отказывала на любом компьютере. Смещение сторожит `ComputerSessionInfoTests`
  (номер сеанса из того же буфера против номера процесса, без окна, идёт в CI).

## Агент и чат (1.37.0, раздел B)

**Браузер агента — WebView2 в своём окне, управление через DOM.** Пакет `Microsoft.Web.WebView2`
только в приложении; ядро говорит с ним портом `IWebBrowser` (`Amarin.Core/Browser`), как с мышью.
Фабрику окна ставит главное окно (`MainWindow.AgentBrowser.cs`, только `IsRealApp`), без неё
`BrowserHub.Open` отдаёт null и агент инструмента `browser` не получает. Сеанс — на прогон агента
(`AgentHost.RunCoreAsync`), окно открывается первым действием и закрывается с концом прогона;
браузер один на процесс (свой `ComputerLease`). Профиль — `browser/` в папке профиля: в архив не
едет, «Удалить все данные» его стирает, куки и пароли и так закрыты правилом `SensitivePaths` по
имени файла. Страница читается скриптом с метками `data-amarin-id` вида `b<чтение>_<n>`: новое
чтение снимает прежние, и устаревший id — отказ «прочитай заново». Нажатия и ввод — доверенными
событиями DevTools (`Input.dispatchMouseEvent`, `Input.insertText`): синтетический `click()` часть
сайтов не принимает. Шлюз — как у мыши (`ToolGate.IsHands`): запись без вопроса в обычном режиме,
SynGuard судит записи и видит страницу (`Agent.GuardPage`), чтения не судит; адрес `open` режет
`BrowserSafety` в `HardBlock` (только интернет: не файлы, не этот ПК и не локальная сеть), и тем же
правилом окно режет переходы, начатые страницей. Пароль агент не вводит — `handoff` показывает
человеку полосу с «Готово» (без человека — отказ). Загрузки страницы — через белый список и
`DownloadAccessBroker`, как у `download_file`. Окно картинок (`ComputerHistory.Trim`) оставляет
модели последнее чтение страницы. Живой прогон — `AgentBrowserLiveTests` (`AMARIN_BROWSER_LIVE=1`).

**Значок под ответом размером в 14 точек.** Значки ряда — `DrawingImage` в `Icons.Dark/Light`, и
картинка растягивается по самой фигуре: у обводки без заливки рамка — это сама обводка, а не бокс
24. Поэтому размер задаёт поле кнопки в `ChatMessageViews.IconAction`: обводке (скобки выгрузки,
ветка, корзина) — 6, иначе она выходит на 18 точек при 13-15 у соседей; толщина обводки
подбирается так, чтобы значок не был светлее соседей.

**Приватность — подстраница «Безопасности» (`PrivacySub`):** шифрование чатов, провайдеры без
хранения данных и срок временного чата. Кнопка временного чата — тёмная «таблетка» со своим
переключателем (`TemporaryChatPlaque`), без строки пояснений.

**Временный чат не пишет хранилище.** Признак `ChatSession.IsTemporary` (`[JsonIgnore]`), охрана —
в `ChatStore.Save`: ни файла, ни описи, ни события `Saved` (значит, ни поиска, ни архива, ни копий).
Список временных — `TemporaryChats` у окна (`MainWindow.Temporary.cs`); в режиме «до закрытия»
(`AppSettings.TemporaryChatsUntilClose`) они стоят своей группой наверху списка, в режиме «сразу»
уход из чата его удаляет (`LeaveTemporary` в `StartNewSession`/`LoadSession`). Черновик временного —
только в памяти (`DraftKey` — свой id, без записи), сводка не считается, Розе текст не уходит,
`deferred_task` отказывает (`AgentRunContext.TemporaryChat`). Журнал аудита и траты пишутся как обычно.

**Ветка в новый чат — `ChatBranchCopy`, не `ChatBranches.Fork`.** Копия через JSON хранилища до
ответа включительно (`ChatSessionEdit.ApiCut`), без спрятанных вариантов, цен, отметок отложенных
задач и разговоров с агентами; сжатие сбрасывается, если граница позже обреза. Кнопка — только у
ответов модели, значок `Branch` в обеих темах значков.

**Разговор с агентом живёт по настройке (`AppSettings.AgentMemory`).** `AgentMemoryBook` (корень
композиции) отдаёт ходу `VeniceTurnContext.Agents`: новый на ответ, общий на чат в памяти или поднятый
из `ChatSession.Agents` (режим «сохранять в чате», до 20 последних). Номер нового агента —
`AgentConversations.Allocate`: счётчик реестра на каждом запуске идёт с a1, а агенты из файла помнят
свои номера; `AgentRegistry` хранит работающих по паре «чат + id». Срок жизни модели называет блок
`ChatEngine.AgentLifetimeRules` в системном промпте, а не описание `message_agent`.

**Скорость модели — `ReasoningChoice.Speed`, таблица — `ModelSpeeds`.** Каталоги уровней не
сообщают, поэтому таблица по провайдеру и семейству; на провод уходит только то, что модель умеет
(`service_tier` у OpenAI и OpenRouter, быстрый — старым именем `priority`; `speed: "fast"` с бетой у
официального API Anthropic), а 400 о поле снимает его повтором. Оценка цены прямых провайдеров
умножается на уровень, каким ответ обслужили (`service_tier` ответа, `usage.speed` у Anthropic).

**Приватность OpenRouter и белый список.** `AppSettings.OpenRouterNoRetention` уходит в каждый запрос
к OpenRouter полем `provider` через делегат `AgentOptions.NoRetention`; пакетные модели при нём идут
мимо очереди (она хранит заявки до 30 дней), Decisions получают тот же фильтр. «Загрузка с любого
сайта» (`AppSettings.DownloadAnySite`) — статика `DownloadValidator.AllowAnySite`, её ставят запуск,
переключатель и смена профиля (`AppServices.UseProfile`). Обе — настройки защиты: в существующий
профиль из архива не приезжают; браузер агента и загрузка с любого сайта сбрасываются и у нового.

## Безопасность и политики (1.37.0, раздел C)

**Аудит автозапуска — `startup_programs audit` (`AutostartAudit`).** Только чтение. Источники:
Run-ключи и папки (`StartupApproval.List`, ярлык раскрывается через `WScript.Shell`), задачи —
`ScheduledTasks` (COM-интерфейс Планировщика; через него же `scheduled_task list/query`: текст
`schtasks` приходил в OEM-странице дочерней консоли, и кириллица становилась «?????» ещё до
программы — на английской системной локали это 437), службы со стартом boot/system/auto из реестра (у
svchost — `ServiceDll`), подписки WMI `root\subscription`, расширения Chrome, Edge, Firefox. Файл из
командной строки достаёт `CommandLinePath` (у хостов — rundll32, оболочки — первый аргумент-файл).
Риск — без подписи, в месте, куда пишет обычный пользователь (`AccessExplain.Decide` для
пользователя, Users, Authenticated Users, Everyone, INTERACTIVE), файла нет, расширение не из
магазина. Подпись — `AuthenticodeCheck.InspectLocal`: без сети и с каталогами Windows (иначе
svchost «без подписи»); `Inspect` для обновления не тронут.

**Цепочка журнала аудита.** У строки поле `prev` — SHA-256 открытого текста предыдущей строки того
же файла байт в байт (`"-"` — первая в файле), без пересборки объекта: иначе пояс и порядок полей
рвали бы цепочку. `Append` под одним замком читает хвост с диска (без памяти о прошлой записи), сериализует,
шифрует, пишет. `Merge` идёт через него же, звено из архива перезаписывается. Импорт архива
дописывает в открытый профиль через живой журнал (`DataBundleImporter.LiveAudit`, как
`LiveLedger`): свой экземпляр писал мимо замка программы, и её строка в ту же секунду терялась. `VerifyChain` показывает вкладка «Аудит» журнала. Конец цепочки не защищён —
для этого копия в журнал Windows.

**Журнал Windows (`AuditEvents`, `WindowsEventLog`).** `ReportEventW`, источник «Amarin Admin AI»
не регистрируется (регистрация требует администратора). Без аргументов и заголовка чата — решение
человека. `AuditLog.Mirror` зовёт только `Record`, ставит только `ApplyProcessWide`: импорт и тесты
в журнал машины не пишут. Настройка `AuditToWindowsLog` (заводская — да) — защита, из архива в
существующий профиль не приезжает.

**Политики организации (`OrganizationPolicy`, `HKLM\SOFTWARE\Policies\Amarin\Admin AI`).**
Читаются раз при запуске в `ApplyProcessWide`, накладываются при чтении, в `settings.json` не
пишутся. Где действуют: «только чтение» и выключенные инструменты — `ToolGate`; мышь — одним
`ComputerHub.Allowed` (новое место, решающее доступ к мыши, берёт его, а не галочку); провайдер —
`VeniceClient.Request`; модель — рядом с `RequireKey` и в цепочках замены; списки —
`ApiKeyProvider.Providers`, `VeniceModelCatalog.ForSlot`, `ModelPickerPanel`, `KeyAddDialog`; копия в
журнал Windows — `AuditEvents.Mirror`. Страница «Безопасность» показывает строку и блокирует
заданное. Шаблон — `policies/*.admx|adml`; новое значение политики — константа, строка в ADMX и
обоих ADML (сверяет `OrganizationPolicyTests`). `release.yml` выкладывает папку вложением
`Amarin-Admin-AI-v<версия>-policies.zip` (шаг «Policy templates»); в `SHA256SUMS` он не входит —
там одна строка про exe, её читает программа.

## Документы, голос, медиа (1.37.0, раздел D)

**WinRT — скриптом PowerShell 5.1, а не проекциями (`Media/WinRtScript`).** TFM без версии SDK, и
переход на `net10.0-windows10.0.x` потянул бы в exe Microsoft.Windows.SDK.NET. OCR
(`Windows.Media.Ocr`), страницы PDF картинкой (`Windows.Data.Pdf`) и перекодирование звука
(`Windows.Media.Transcoding`) идут отдельным процессом, как Bluetooth. Процесс запускается
`PowerShellProcessRunner` напрямую, мимо `PowerShellHelper.RunAsync`: файл лежит здесь, а
`RunAsync` унёс бы скрипт на удалённую машину чата. Языки OCR ставит Windows («Распознавание
текста» в языковом пакете); нет — отказ со списком установленных.

**PowerPoint.** `SlidesTemplate` — каркас разметкой (тема, мастер, две раскладки, мастер заметок),
`SlideBuilder` — слайды деревом OpenXml, один на создание и правку. Заголовок и тело — заполнители
раскладки, у чужой презентации — её раскладки. Слайд начинают H1/H2 и `---`; последний абзац
«Notes:» — заметки, как их показывает `SlidesReader`. Размер шрифта подбирается прикидкой объёма:
`normAutofit` PowerPoint применяет только при правке. Слайд упоминают и разделы (`p14:sectionLst`),
и произвольные показы — вставка и удаление идут через `SlideList`, иначе «восстановить файл».
Мастер заметок доставляется при первой заметке (`EnsureNotesMaster`).

**Анализ таблиц считает программа (`TableQuery`, `analyze_table`).** CSV — существующим
`ExcelWriter.FromDelimited` (переносы строк в кавычках он не понимает), Excel — видимыми значениями
через `DocumentConvert.ExcelTables` (с посчитанными формулами). Числа читаются в русской записи:
одна запятая без точки — дробная часть. Пустые при сортировке — в конце в любом направлении.

**Диаграмма в чате — блок ```` ```chart ````, а не картинка** (так решил человек). Формат и
пределы — `ChartSpec` (≤8 рядов, ≤200 точек, у круга один ряд), разбор терпит лишние запятые.
Рисует `ChatChartView` одним проходом `DrawingContext`; цвета рядов — существующие ключи палитры
(акцент и цвета подсветки кода), новых ключей у 50 палитр нет. Недописанный блок остаётся кодом.
Прикидка высоты (`MessageHeightEstimate`) знает о диаграмме. Диаграмма Excel — `ExcelCharts`
(`edit_document add_chart`): ряды ссылаются на ячейки, значения ещё и в кэше.

**Голос по-русски — облаком.** Русского распознавателя SAPI в Windows нет вовсе, поэтому «Авто»
без выбранной модели берёт Whisper Large V3 у Venice, иначе у OpenRouter
(`VoiceAvailability.CloudModel`), а строка под «Распознаванием» называет, что распознаёт сейчас или
почему нечем (`VoiceRoute`). Модели и языки на подстранице — списками; каталоги аудиомоделей —
`AudioModelCatalog` (открытые `models?type=tts|asr` у Venice и `models?output_modalities=speech|transcription`
у OpenRouter, свой клиент без ключа, спрашиваются при показе подстраницы). Поля, сохраняемые с потерей
фокуса, пересчитывают микрофон через `VoiceSettings.Changed`: пересчёт на закрытии настроек по Esc
видел прежнее значение.

**Озвучка — System.Speech (`SpeechOutput`) или модель провайдера (`AppSettings.SpeechModel`).**
SAPI создаётся при первом чтении и видит только свои голоса. Модель Venice или OpenRouter читает
через `VeniceClient.SpeakAsync` (`audio/speech`, MP3) частями по предложениям (`SpeechText.Chunks`),
следующая часть озвучивается, пока звучит текущая; звук играет `MediaPlayer` из временного файла.
Цену ответ не называет — она считается по цене знака из каталога и помечается оценкой. Текст для чтения — `SpeechText`
(без кода, таблиц, формул и диаграмм). Читает только кнопка под ответом (`MainWindow.Speech.cs`):
разговорный режим голосом был в 1.37.0-beta и удалён по решению человека — не возвращать его без просьбы.

**Запись и видео во вложениях расшифровываются сразу (`MainWindow.Transcribe.cs`).** Звук в чат не
попадает: `MediaAudio` перекодирует во временный WAV 16 кГц моно, `WavFile.Pieces` режет его
потоком по 5 минут, каждая часть идёт тем же `RecognizeAsync`, что голосовой ввод, итог —
текстовое вложение с метками времени. Esc и смена чата отменяют, временный файл удаляется всегда.

**Снимок области — глобальное сочетание `region-screenshot` (`RegionSnip`).** Экран снимается до
показа выделения; на каждом мониторе своё окно в физических пикселях, `WM_DPICHANGED` гасится, как
у `ComputerGlow`. Перевод рамки в пиксели — `RegionSnip.ToPixels` (масштаб — монитора, не
программы). Сочетание по умолчанию не назначено.

## Как проверять интерфейс, не запуская программу

Запускать exe ради проверки почти никогда не нужно, а часто и вредно: окно вылезет поверх того,
чем человек занят. Всё проверяется тестами на живом WPF:

- Класс с окнами помечается `[Collection(WpfCollection.Name)]`, работа идёт внутри
  `_wpf.Ui.Invoke(...)`. **Читать свойства `DependencyObject` можно только внутри этого вызова** —
  снаружи будет «поток не владеет объектом».
- Внешний вид снимается в картинку: `RenderTargetBitmap.Render(element)` и `PngBitmapEncoder`
  во временную папку. Так проверялись формулы и углы окна, не показывая ничего на экране.
- Геометрию настоящего окна меряют через `GetWindowRect`/`GetMonitorInfo` в тесте, а не на глаз.
- Мышь имитируется `RaiseEvent` с `MouseButtonEventArgs { RoutedEvent = UIElement.PreviewMouseDownEvent }`.

Если правите файл с обратными слэшами (LaTeX, пути Windows, регулярки) — правьте его файловым
инструментом. Скрипты в оболочке съедают слэши, и в исходник попадает `\(` вместо `\\(`.

## Соглашения

- Комментарий объясняет **почему**, а не что делает строчка. Хороший комментарий здесь называет
  причину, из-за которой сделано именно так: какой баг это чинит, что сломается иначе.
  Пересказ кода словами не нужен.
- XML-документация у публичных типов и у всего неочевидного; в `<remarks>` — предыстория решения.
- Ошибку показываем человеку понятной строкой, а не текстом исключения. Сетевой сбой, отказ
  пользователя и повреждённый файл — обычные ответы, а не аварии.
- Отказ инструмента — тоже ответ модели: она читает его текст, поэтому в нём пишут, что делать
  дальше («не повторяй попытку», «домен остался заблокированным»).
- На каждое исправленное поведение — тест, который падал бы до правки. Особенно на то, что нельзя
  увидеть глазами: границы окна, разбор чужого JSON, порядок закрытия попапов.

## Осторожно

- **Программа на пользователя одна.** `SingleInstance` берёт `Local\`-мьютекс в `Program.Main`
  до всего остального; второй запуск кладёт свой `--prompt` в `handoff/` и будит первого
  широковещательным сообщением. `--smoke-tools` решается **до** замка — консольный прогон
  инструментов обязан работать при запущенной программе. Там же, до замка, живут
  `--apply-update` (подмена exe от администратора, её просит как раз держатель замка) и
  `--await-exit <pid>`: перезапуск после обновления обязан дождаться выхода прежнего процесса,
  иначе новый видит живого владельца, отдаёт ему запрос и выходит — оба процесса исчезают, и
  человек остаётся без окна. Тоже до замка — `--rollback-update` (откат от администратора) и
  `--smoke-report <файл>` (прогон инструментов с итогом в файл, без консольного окна: программа
  оконная, и окно `AllocConsole` раннер CI не читает). С 1.28.0 `--prompt` только кладёт текст в поле — и при первом
  запуске, и при передаче открытому окну; отправляет явный `--send`, и флаг едет в `handoff/`
  вместе со своим запросом. `--wipe <метка>` — см. «Удалить все данные» стирает преемник.
  `--wake` (1.33.0) — запуск Планировщиком к сроку отложенной задачи: при работающей программе
  молча выходит, как `--tray`; иначе стартует в трей или свёрнутым без активации, а окно пароля
  приходит свёрнутым с подсказкой.
- **Автообновление доводится после закрытия окна.** Проверка — при каждом запуске. Закрытие
  любым путём при включённой галке и найденной версии прячет окно (`IExitHost.HideForBackgroundExit`),
  а процесс без окна дожидается проверки и загрузки, подменяет файл и выходит (`UpdateExit`,
  потолок `UpdateSchedule.ExitLimit`). Если удачной проверки в этом запуске не было или она
  старше `UpdateSchedule.RecheckOnExit`, выход спрашивает GitHub ещё раз — уже без окна. Замок единственного экземпляра всё это время у него,
  поэтому второй запуск обязан вернуть окно (`UpdateExit.Revive`), а начатая подмена —
  поднять новую версию после себя. Спрятанное окно Windows отдаёт как «скрыто»: геометрию
  снимают до `Hide()`, не после.
- **Опасные действия подтверждает человек.** Решает `ToolGate`, текст вопроса собирает
  `DangerousActionGuard`, спрашивает `ConfirmationQueue` — адресно: у запроса есть `SessionId`,
  и отмена одного чата не должна убивать вопросы соседнего (`CancelForSession`, а не
  `CancelAll`); отвечают показанному запросу (`Complete(request, …)`), а не голове очереди.
  Новый инструмент, который пишет в систему, добавляется в таблицу `ToolEffects`, а не в обход
  шлюза. Режимов четыре (`ApprovalMode`: обычный, «спрашивать всё», «только чтение»,
  «подтверждать всё автоматически»); последний — осознанный выбор пользователя, но постоянные
  изменения настроек (белый список загрузок) спрашиваются всегда, а PowerShell разрешается
  впрок только до конца хода, не на весь чат.
- **Текст из сети — данные, а не указания.** `web_search`, `scrape_url`, `youtube_transcript`
  приносят в контекст чужой текст, а тот же агент вызывает PowerShell и реестр. С 1.28.0 это
  правило есть и в самом промпте агента.
- **Промпт агента сохраняется копией.** Кнопка «Сохранить» кладёт текст в
  `AppSettings.TechAgentPrompt` целиком, даже нетронутым; нетронутые копии прежних умолчаний
  узнаёт `LegacyAgentPrompts` и сбрасывает. Меняете `Agent.BaseSystemPrompt` — прежний текст
  дописывается туда. Язык интерфейса агенту называет приписка `BuildMachinePathsPrompt`, а не сам
  промпт: так он доходит и до сохранённого человеком текста.
- **Секреты не коммитим.** Ключей может быть несколько, у разных провайдеров. Свои лежат в `keys.json`
  в папке профиля, зашифрованные DPAPI на текущего пользователя Windows (`DataProtector`,
  `ApiKeyStore`); открытым текстом ключ на диск не попадает нигде. Ключи из `VENICE_API_KEY`
  и `OPENROUTER_API_KEY` (или user-secrets) остаются и стоят в списке первыми, и в `keys.json`
  не переписываются: человек сознательно держал их снаружи. Переименовать и убрать из списка
  можно любую строку, включая эти, но переменную окружения программа не трогает: у неё
  запоминается отпечаток (`HiddenEnvironmentKeys`), и брать этот ключ она перестаёт. Отпечаток,
  а не идентификатор строки, — иначе сменённое значение переменной осталось бы под запретом
  молча. Вставить убранный ключ заново `Add` не даёт (это была бы копия переменной на диске) —
  его возвращает `Restore` из строки под списком. Название строки окружения, наоборот, живёт
  по месту (`EnvironmentLabels`): его дают переменной, а не значению. В `appsettings.json` ключа нет
  и быть не должно: этот файл лежит в git и уезжает в релиз — там лишь адрес API, модель
  по умолчанию и заготовка белого списка загрузок. `keys.json` не попадает в архив данных
  (`DataBundle.CategoryOf`) — его человек пересылает. Журнал трат попадает (1.35.0): в имени
  файла отпечаток ключа, а не сам ключ.
- Файлы пользователя (`%APPDATA%`) в тестах не трогаем — только временные папки.
